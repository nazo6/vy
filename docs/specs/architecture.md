# 全体アーキテクチャ設計

Vy は、Vimのモーダル編集の軽快さと、VS
Codeの拡張性・リッチUI体験を両立するため、**「GPUIフロントエンド」** と
**「エディタコア/バックエンド」**
を完全に物理分離するクライアント/サーバー構成を採用しています。

---

### 1.1 プロセスの構成

ローカル接続とリモート接続のどちらでも、クライアントとコアは別のプロセスです（[ADR 0002](../adr/0002-process-model.md)）。

| 接続   | クライアント | コア                                         | 経路             |
| :----- | :----------- | :------------------------------------------- | :--------------- |
| local  | `vy-app`     | `vy-app` が起動した `vy-server` の子プロセス | 標準入出力       |
| remote | `vy-app`     | SSH の先で起動した `vy-server`               | SSH の標準入出力 |

リモート接続は `ssh -T [-p port] [user@]host -- <serverPath> --stdio`
で起動します。 接続先には導入済みの `vy-server`
を使い、バイナリの自動転送は行いません。接続先は `~/.config/vy/connections.json`
のプロファイルで選びます （[ADR 0010](../adr/0010-remote-connection.md)）。

`fs`、`process`、検索、文書の読み書きは常にコアが行います。ローカル接続でも、ファイルを開くのはコアのプロセスです。クライアントが行うのは、キー入力の照合、描画、Webview
の表示、クライアント側の QuickJS の実行です。

同一プロセスでコアを呼ぶ近道は作りません。近道を作ると、リモート接続でだけ壊れる経路が残るためです。

### 1.2 起動と終了

- クライアントは `vy-server --stdio`
  を子プロセスとして起動します。ワークスペース、ログの出力先、再開するセッションは
  `initialize` の params で渡します（[`protocol.md`](./protocol.md)）。
- `vy-server`
  が終了したとき、クライアントは落とさず、通知を出して自動で再接続します。手動の
  `vy.reconnect_server` も用意します。
- 再接続は新しいセッションです。コアはワークスペースごとに保存したレイアウトを
  読み直し、クライアントは `layout/get` と `sync/request`
  で開いていた文書を戻します。
  未保存の本文はクライアントから送り、アンドゥ履歴だけ捨てます
  （[ADR 0010](../adr/0010-remote-connection.md)）。
- 保存済みの文書はコアがディスクから読み直します。ディスク上の内容が変わっていた場合は、
  コアが返した本文と version をクライアントが採用します。
- セッションを復元した起動では最初の `buffer/snapshot`
  がありません。クライアントは `sync/request` の応答後に `init.ts`
  を評価し、キーバインドと設定を適用します。
  再接続では評価済みの登録をそのまま使います。
- `ui`
  ビューのウィジェット木はクライアントが持ちます。レイアウトを復元するときは、
  コアが返したビュー ID に一致する最後の木をクライアントが付け直します。

### 1.3 実行基盤

- `vy-server` は tokio
  を使います。標準入出力の読み書き、セッション、タイマーを非同期のタスクで回します。
- `vy-core` は非同期ランタイムに依存しません。同期の API だけを持ち、`vy-server`
  がタスクから呼びます。ヘッドレスのテストで同じコードを動かすためです。
- `vy-app` は GPUI の executor を UI に使い、RPC
  の読み書きは専用のスレッドで行います。書き込みはキューに積み、UI
  スレッドをブロックしません。受信は非同期チャネルで GPUI
  のタスクへ渡し、メッセージが届いたときだけ画面を更新します。
- `init.ts` と各プラグインは、それぞれの QuickJS ランタイムで動きます。QuickJS
  は同期なので、ホストがジョブキューを回して Promise を進めます。API は
  ホストがインストールするグローバル `vy` で、仮想モジュールはありません
  （[ADR 0019](../adr/0019-global-vy-api.md)）。ソース形態のプラグインは、
  プラグインのディレクトリをルートに相対 import を解決します
  （[ADR 0020](../adr/0020-plugin-source-and-bundles.md)）。
- JS から状態を読む・変える呼び出しは `HostRequest` で UI に渡し、UI が
  `HostReply` を返します。JS スレッドは応答を待ちますが、UI
  は待ちません。初期化は 1 秒、コマンドは 5 秒、応答は 5 秒で打ち切り、メモリは
  64 MiB に制限します。
- `init.ts` は Oxc で型だけを除去してから評価します。型注釈、interface、generics
  を取り除くだけで、構文の変換はしません。位置付きのエラーを返し、壊れた
  スクリプトでもアプリは落ちません。

## 2. エディタ本体（Core）とプラグインの責務境界

| 機能                             | 担当                             | 理由                                                                                       |
| :------------------------------- | :------------------------------- | :----------------------------------------------------------------------------------------- |
| **LSPクライアント基盤**          | **エディタ本体 (Rust)**          | プロセス起動・JSON-RPC通信・ドキュメント同期・診断エラー集約をRustネイティブで堅牢に実行。 |
| **Tree-sitter (構文解析)**       | **エディタ本体 (Rust)**          | ハイライト描画、インクリメンタルパース、ASTテキストオブジェクトをRustの描画ループと直結。  |
| **Rope、本文の版、アンドゥ履歴** | **エディタ本体 (Rust)**          | `ropey` による本文と version。アンドゥは、整形や複数ファイルの編集も含めて1か所で持つ。    |
| **Git状態の監視**                | **エディタ本体 (Rust)**          | ファイル変更監視と連動したガターのDiff表示。                                               |
| **ペインのレイアウト**           | **エディタ本体 (Rust)**          | 分割、比率、フォーカス、フローティングを1か所で持ち、保存と復元を同じ形で行う。            |
| **ペインの中身（ビュー）**       | **プラグイン/設定 (TypeScript)** | ビューの登録とウィジェット木の提供。描画とキー入力はクライアントが行う。                   |
| **設定・キーバインド・UI拡張**   | **プラグイン/設定 (TypeScript)** | `init.ts` で柔軟にキー割り当てや外観を制御。                                               |

## 3. UIレンダリング: GPUI + `gpui-kit/webview`

採用の理由と比較は [ADR 0001](../adr/0001-ui-framework.md)
に記録しました。要点だけを書きます。

- **メイン画面**: GPUI を使います。macOS は Metal、Windows は Win32 と
  DirectWrite、Linux は Wayland と X11
  で動きます。バージョンは固定し、更新は独立した PR で行います。
- **薄いレンダラ**:
  文書、ペインの構成、フォーカスはコアが持ちます。カーソル、選択、モード、スクロールはクライアントが持ちます。クライアントは、その状態を描画する層にします。フレームワークの宣言的
  API は周辺の UI に限定し、エディタ本体は低レベル API で描きます。
- **リッチコンテンツ / Webview**:
  [`gpui-kit/crates/webview`](https://github.com/longbridge/gpui-kit/tree/main/crates/webview)
  を薄いラッパ越しに使います。OS ネイティブの Webview（`wry` ベース）を GPUI
  のレイアウトツリーに重ねます。
  - Jupyter Notebook のセル出力
  - Markdown / HTML プレビュー
  - 外部サービスの埋め込み（地図、グラフ）

プラグインは固定のサイドバーやパネルを追加できません。ビューを登録し、ペインとして開きます。`ui`
ビューではウィジェット木を渡し、描画、フォーカス、キー入力をクライアントに任せます。ビューの中の一部は、スロットにデータを渡して差し替えます。GPUI
の要素を JS から作ることはできません。

Webview は最終手段です。Web の文書そのものを表示するときだけ使い、操作を伴う UI
には `ui` ビューを使います。Webview
はキー入力とフォーカスを自分で持ち、キーマップ、モード、IME
の前編集を共有できないためです。UI の作り方は [`ui.md`](./ui.md)、API の一覧は
[`api.md`](./api.md) の「ペインとビュー」にあります。

### 3.1 状態の所在

編集の状態は、キー入力のたびに変わるものと、文書に属するものに分けます（[ADR 0003](../adr/0003-editor-state.md)）。

| 状態                                                           | 持つ場所     | 理由                                                         |
| :------------------------------------------------------------- | :----------- | :----------------------------------------------------------- |
| 本文、version、ファイル                                        | コア         | 複数のペインと接続で共有する。ファイルはコアの環境にある     |
| カーソル、選択、モード、スクロール、折りたたみ                 | クライアント | キー入力のたびに変わる。ペインごとに違い、描画にしか使わない |
| ペインの構成、ペイン間のフォーカス、ウィンドウ                 | コア         | 接続とセッションの復元で同じ形にする                         |
| `ui` ビューのウィジェット木とウィジェットのフォーカス          | クライアント | 入力のたびに変わる。描画にしか使わない                       |
| 診断、構文、Git の状態                                         | コア         | 言語サーバーとファイル監視の結果である                       |
| IME の前編集                                                   | クライアント | OS の入力から直接届く。確定してから本文に入る                |
| コマンドパレットと Ex の入力、履歴、補完候補、引数のプロンプト | クライアント | 入力中だけの状態。実行は共通のコマンド経路へ渡す             |
| 設定の各層とウィンドウごとの上書き                             | クライアント | 表示とコマンドの実行に使う。コアへは必要な値だけ送る         |

カーソルと選択をコアに置くと、1文字動かすたびに往復が入ります。リモートでは、その往復がそのまま入力の遅延になります。

コアに位置が要る操作（補完、ホバー、LSP、整形）は、呼び出しのたびに位置を渡します。常時は同期しません。

アンドゥの履歴はコアが持ちます（[ADR 0004](../adr/0004-undo-in-core.md)）。言語サーバーの整形や、複数ファイルの置換も同じ履歴に入れるためです。

カーソルと選択はクライアントが持つため、編集を送るときに前後の選択を一緒に渡します。コアは本文の逆編集と選択を1つの項目として積み、アンドゥのときは逆の編集と選択を返します。

編集はクライアントが先に適用し、`base_version`
を付けてコアへ送ります。コアが受け付けない場合は本文を送り直し、カーソルは再同期の結果に合わせます。このとき、その文書のアンドゥ履歴は捨てます。同じ文書を2つのペインで開いても、カーソル、選択、折りたたみ、スクロールはペインごとに独立です。

### 3.2 位置の表現

- プロトコルと API の位置は、0 始まりの行と UTF-16 のコード単位です。JS
  の文字列と数え方を揃えるためです（[`api.md`](./api.md)）。
- コアの内部では、ropey の char index
  と行番号で持ちます。行の追加や削除で全体を数え直さずに済み、byte と UTF-16
  のどちらにも変換できるためです。
- tree-sitter に渡すときは UTF-8 のバイト、LSP に渡すときは UTF-16
  に変換します。変換は境界の1か所にまとめ、各所で数え方を混ぜません。

## 4. ペインとレイアウト

固定のサイドバーやパネルは作らず、画面に出るものはすべてペインとします。ウィンドウ（タブ）がレイアウト木を持ち、ペインはその葉かフローティングです。レイアウトはコアが持ち、クライアントは確定した木を描画します。

モデル、操作の意味論、API、メッセージ、保存の単位は [`panes.md`](./panes.md)
にまとめました。ペインの中のフォーカスとキー入力は [`ui.md`](./ui.md)
にまとめました。レイアウトと開いていた文書の URI は、ワークスペースごとに
`<データ>/workspace-state/<workspace-hash>.json` へ保存します。

## 5. URI とリモートのパス

ファイルを指す値は、文字列のパスではなく URI で扱います。

| スキーム | 用途                                                   |
| :------- | :----------------------------------------------------- |
| `file:`  | 実在するファイル。リモート接続では接続先のパスを指す   |
| `vy:`    | 未保存の文書、差分、プレビューなど、実体を持たない文書 |

リモート接続では、`file:` の URI
をクライアントがそのまま解釈しません。パスの区切りと大文字小文字の扱いが OS
で違うためです。変換はコアが行い、クライアントは URI
を不透明な値として扱います。

複数のルートを持つワークスペースに対応するため、`workspace.folders()`
は配列を返します。設定の `.vy/settings.json`
は各ルートの直下に置き、ルートごとに解決します。

## 6. 依存の境界

```text
vy-app  --->  vy-proto
  |  \--> vy-core
  |  \--> vy-client-api ---> vy-host-api
  |  \--> vy-host-api
  |  \--> vy-js  ----->  rquickjs, Oxc (外部クレート)
  |         \--> vy-host-api
  |  \--> vy-capabilities

vy-server ---> vy-core --->  ropey
          \--> vy-proto
          \--> vy-host-api
          \--> vy-js        (Phase 6 で追加)
```

`vy-host-api` はクライアントとコアで共有する params / reply / イベント payload
の型と メソッド宣言を持ちます。`vy-client-api` は
`ui`、`views`、`keymap`、`commands`、 `editor`
などクライアント専用の型と宣言を持ちます。どちらもハンドラを持たず、
クライアントは `vy-app/src/api`、コアは `vy-server/src/api` にハンドラを置きます
（[ADR 0012](../adr/0012-shared-host-api.md)）。

名前空間は trait として宣言し、`HostApi`（共有）と `ClientHostApi`（共有 +
クライアント専用）の facade が `dispatch` をまとめます。ホスト構造体は名前空間
trait を 実装するだけで、メソッドごとの adapter を持ちません
（[ADR 0013](../adr/0013-host-api-traits.md)）。

- `vy-app` だけが GPUI に依存します。CI で `cargo tree` を検査し、他のクレートが
  GPUI を引いたら失敗させます。
- `vy-core`
  は描画に依存しません。ヘッドレスのテストと、リモートのサーバーで同じコードを動かすためです。
- `vy-js` はクライアントとサーバーの両方で使える形にし、GPUI にも RPC
  にも依存させません。Phase 2 で使うのはクライアントだけです。
- `vy-capabilities` はマニフェストの宣言と承認の記録だけを持ちます。検査は JS
  のシムではなく Rust で行います。

## 7. 状態の流れ

1. キー入力はクライアントのキーマップが照合します。
2. コマンドはクライアントで開始します。UI
   だけで完結するものは、そのまま反映します。
3. 文書を変更するコマンドは、コアに編集を要求します。
4. コアが編集を適用し、version を上げて通知します。
5. クライアントは通知を受けて表示を確定します。手元で先に描いていた場合は、version
   が合ったときだけ確定します。
6. プラグインのイベントは、確定した変更に対して発火します。

この順序により、コアが正であることと、入力時に画面が止まらないことを両立します。

`init.ts` のコマンドも同じ経路です。JS のハンドラは `editor.edit`
などをホストへの要求として返し、UI
が同じトランザクションの形でコアへ送ります。JS
から本文を直接書き換える経路はありません。

## 8. 未決定事項

- クライアントの先読み描画をどこまで許すか。入力のたびに確定を待つと、リモートで遅延が見えます。
- `vy-server`
  を1つのプロセスで複数のワークスペースに使うか、ワークスペースごとに分けるか。
- 接続先の `vy-server` を自動で更新するか。Phase 5 では導入済みのものを使い、
  版が合わなければエラーにします（[ADR 0010](../adr/0010-remote-connection.md)）。
- `vy-server` の並行ディスパッチ。リクエストごとに `tokio::spawn`
  するか、version の順序を保つために文書ごとのキューにするか。大きな `pane/open`
  を `spawn_blocking` に回すかは、先に決めます。
- Oxc を常にビルドするか、`ts` feature
  で切れるようにするか。現状は常時有効です。
