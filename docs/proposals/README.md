# 提案・検討メモ (Proposals)

まだ決まっていないアイデアや未決定事項、**まだ着手していない計画**を置く場所です。
仕様書（`docs/specs/`）を「現在の確定仕様」だけに保つため、「これからどうするか悩んでいること」や「未実装機能の計画」はここに集約します。着手した作業の記録は [`../worklogs/`](../worklogs/README.md) に移します。

## ファイルの構成

提案は「まだ決めていないこと」と「決定済み事項の未着手の実装計画」の 2 種類があります。どちらも次の順で書きます。

```markdown
## 1. 決定済みの前提

- 決定済みの内容は再掲せず、ADR を参照します（`related_adrs` にも書きます）。
- ここに書けるのは、決定の要約 1〜2 行と ADR へのリンクだけです。

## 2. 未決定の論点

- 選択肢、判断に必要な材料、決める人・時期を書きます。

## 3. 作業計画（着手する場合）

- 作業順序、対象ファイル、検証方法を書きます。

## 4. 完了条件

- 何ができたら `status: "closed"` にし、どの ADR / 仕様書へ反映するかを書きます。
```

- `related_adrs` は、決定済みの ADR を実装する提案では必須です。決定がまだ無い提案では省略できます。
- 実装計画に決定（「〜する」）が混ざったら、決定は ADR に切り出します。方向性が決まった時点で ADR を作り、proposal は作業計画だけを残します。

## 運用ルール

個人開発のため、厳密なフローは設けません。

1. **書く**: 悩んでいることや設計案、まだ着手していない計画を思いついたら、ファイルを作ってメモします（`status: "open"`）。
2. **着手したら**: 実施内容と結果は [`../worklogs/`](../worklogs/README.md) に記録し、この提案は計画の参照元として残します。
3. **決まったら**:
   - 設計方針が決まったら ADR（`docs/adr/`）や仕様書（`docs/specs/`）に反映します。
   - この提案ファイルは `status: "closed"` にするか、役目を終えたら削除しても構いません。

**未着手かどうかが proposals と worklogs の境目です。** これからやる計画と未決定事項は proposals、着手した作業の日付入り記録・実測値・つまずきは worklogs に置きます。

## 命名規則

ファイル名は `NNNN-<short-title>.md` とします（例: `0001-phase-6-remote-plugins.md`）。
