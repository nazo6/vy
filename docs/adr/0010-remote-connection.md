# ADR 0010: リモート接続の寿命、再接続、配備

- 状態: 採用
- 日付: 2026-10-24

## 文脈

Vy はクライアントとコアを常に別プロセスにしています（[0002](./0002-process-model.md)）。
ローカル接続は子プロセスの標準入出力を使います。リモート接続でも同じ RPC を流しますが、
次の点が決まっていませんでした。

1. SSH の接続が切れたとき、コアのプロセスとセッションをどう扱うか。
2. 再接続したとき、開いていた文書とレイアウトをどう戻すか。
3. コアが失った未保存の編集をどう扱うか。
4. 接続先の `vy-server` をどう用意するか。
5. 接続先をどこに保存し、どう選ぶか。

## 決定ドライバ

1. リモートでだけ壊れる経路を作らないこと。
2. 接続が切れてもクライアントを落とさず、作業を続けられること。
3. まず動く最小の構成にし、常駐デーモンは必要になってから足すこと。
4. 接続先に余計なファイルを置かずに済むこと。
5. 失敗したときに、利用者が原因を特定できること。

## 検討した選択肢

### セッションの寿命

| 選択肢                          | 内容                                                    | 評価                                               |
| :------------------------------ | :------------------------------------------------------ | :------------------------------------------------- |
| A. 再起動 + 再同期（採用）      | SSH が切れたら `vy-server` を起動し直し、状態を送り直す | 実装が小さく、SSH の標準入出力と相性がよい         |
| B. 常駐デーモン + Unix ソケット | 接続先で `vy-server` を常駐させ、`ssh -L` でつなぐ      | セッションを保持できるが、配備と認証の設計が増える |
| C. 手動再接続                   | 切断時は通知だけ出す                                    | 最小だが、リモートでは現実的でない                 |

### 未保存の編集

| 選択肢                          | 内容                                                         | 評価                                           |
| :------------------------------ | :----------------------------------------------------------- | :--------------------------------------------- |
| A. クライアントから復元（採用） | 再接続時にクライアントの本文を送り、コアのバッファを作り直す | 未保存の作業を失わない。アンドゥ履歴だけ捨てる |
| B. 失う                         | コアだけを正とし、保存済みの内容に戻す                       | 実装は小さいが、リモートでは損失が大きい       |

### レイアウトの復元

| 選択肢                  | 内容                                                     | 評価                                                         |
| :---------------------- | :------------------------------------------------------- | :----------------------------------------------------------- |
| A. コアが永続化（採用） | ワークスペースごとにレイアウトと開いていた文書を保存する | [`panes.md`](../specs/panes.md) の方針と一致する             |
| B. クライアントが再構築 | `pane/open` を並べて木を作り直す                         | サーバー側は小さいが、クライアントに分割の再生ロジックが要る |
| C. `session/restore`    | クライアントが木を送る                                   | コアが状態の正を持つ方針から外れる                           |

### 配備

| 選択肢                    | 内容                                                           | 評価                                         |
| :------------------------ | :------------------------------------------------------------- | :------------------------------------------- |
| A. 導入済みを使う（採用） | `PATH` かプロファイルの `serverPath` にある `vy-server` を使う | 実装が小さく、版の管理を利用者に任せられる   |
| B. 自動転送               | 初回接続時にバイナリを送る                                     | 版・ハッシュ・部分転送の設計が増える         |
| C. `vy remote install`    | 配備専用のコマンドを作る                                       | 便利だが、再接続の本体より先に作る必要はない |

## 決定

### 1. 接続方法

- リモート接続は `ssh -T [-p port] [user@]host -- <serverPath> --stdio` で起動します。
- 認証はシステムの `ssh` に任せます。Vy はパスワードや鍵を扱いません。
- 接続先の `vy-server` は、プロファイルの `serverPath`、なければ `PATH` の `vy-server` を使います。
  見つからない場合や版が合わない場合は、接続を閉じてクライアントに英語のエラーを表示します。
- バイナリの自動転送は行いません。必要になったら `vy remote install` を独立した変更として足します。

### 2. 接続プロファイル

`~/.config/vy/connections.json` にプロファイルを置きます。

```json
{
  "profiles": {
    "dev": {
      "host": "example.com",
      "user": "nazo",
      "port": 22,
      "workspace": "/home/nazo/project",
      "home": "/home/nazo",
      "serverPath": "vy-server"
    }
  }
}
```

- `vy-app --connect <name>` で選びます。指定がなければローカル接続です。
- `workspace` は接続先の絶対パスです。クライアントは `file:` URI をローカルパスとして解釈しません。
- `home` は `${home}` の展開にだけ使います。省略した場合、`${home}` を含むケイパビリティは一致しません。
- 接続先の表示名にはプロファイル名を使います。

### 3. 再接続と再同期

- クライアントは接続が切れたら、指数バックオフで自動的に再接続します。手動の
  `vy.reconnect_server` も用意します。
- 再接続は新しいセッションとして扱います。`resume_session` は使いません。
- コアはワークスペースごとに、レイアウト木、ペイン、開いていた文書の URI を
  `<データ>/workspace-state/<workspace-hash>.json` に保存します。`initialize` のときに読み直します。
- クライアントは `initialize` のあと `layout/get` でレイアウトを取り、開いている文書を
  `sync/request` で送ります。
- `sync/request` には、文書の URI、クライアントの version、保存済み version、そして
  未保存の文書だけ本文を含めます。コアは未保存の本文でバッファを作り直し、アンドゥ履歴を捨てます。
- 保存済みの文書はコアがディスクから読み直します。ディスク上の内容が変わっていた場合は、
  コアが返した本文と version をクライアントが採用します。
- 再接続で document ID と pane ID は変わり得ます。クライアントは URI で対応づけます。

### 4. プロトコル

- `PROTOCOL_VERSION` を 3 に上げます。
- `initialize` に `workspace` と `resume_session` があり、`initialized` に
  `server_capabilities` と `platform` が入ります。
- `layout/get` のペイン情報に `uri` を足します。
- `sync/request` を追加します。
- `server_capabilities` には、実装済みの `stream`、`session-restore` などを入れます。
  クライアントは無い機能を呼びません。

## 帰結

### 良い面

- SSH の標準入出力だけでリモート接続が成立し、ローカルと同じ RPC を使えます。
- 接続が切れてもクライアントは落ちず、未保存の編集も戻せます。
- レイアウトの保存場所がコアに一本化され、接続先が変わっても同じ形で復元できます。
- 接続先に Vy の設定ファイルを配る必要がありません。

### 悪い面

- SSH が切れるとコアのプロセスは終了するため、再接続のたびに文書を開き直します。
- 未保存の本文をクライアントから送るため、大きな文書では再接続に時間がかかります。
- 常駐デーモンに比べると、接続直後の応答は遅くなります。

### 緩和策

- `sync/request` は未保存の文書だけ本文を送り、保存済みの文書はコアに読ませます。
- 再接続の状態をステータス行に出し、失敗した理由を英語のメッセージで残します。
- 常駐デーモンが必要になったら、Transport に Unix ソケットを足す別 ADR を作ります。

## 見直しの条件

1. 再接続のたびに文書を開き直す費用が無視できない。
2. ネットワークが不安定な環境で、未保存本文の再送が帯域を圧迫する。
3. 複数のウィンドウで同じワークスペースにつなぐ要求が出る。

## 関連する未決定事項

- 常駐デーモンと Unix ソケットの導入時期。
- バイナリの自動配備と版の管理。
- リモートの `${home}` をプロファイル以外から解決する方法。
- 複数ウィンドウと複数セッションの多重化。
