# ADR 0034: 既定キーマップをスコープとプロファイルの 2 層に再構成する

- 状態: 提案
- 日付: 2026-10-28
- カテゴリー: maintenance
- 実装: 未着手（本ドキュメントの「実装計画」を参照）

## 文脈

`builtin/keymaps/default.json` は 147 件のバインディングを平坦な配列で持ちます。各要素が `keys`・`command`・`when` を 1 組持つため、条件がキーごとに繰り返されます。ADR 0024 と ADR 0032 でコンテキスト（`paneKind`、`overlay`、`uiRole`）を導入した結果、この繰り返しが顕在化しました。

現状を計測した結果は次のとおりです。

| 指標                            | 値                                    | 補足                                                              |
| :------------------------------ | :------------------------------------ | :---------------------------------------------------------------- |
| バインディング数                | 147                                   | 1 行 5 行（整形後は平均 5 行）                                    |
| ファイル行数                    | 736                                   |                                                                   |
| 異なる `when` 文字列            | 17                                    | 実際の条件は 16 スコープに収まる                                  |
| 最頻条件の反復                  | 44 回                                 | `paneKind == 'editor' && overlay == 'none' && (mode != 'insert')` |
| 同一スコープ内のキー衝突        | 0 件                                  | 「後勝ち」に依存している箇所は無い                                |
| 複数スコープに現れるコマンド    | 11                                    | `vy.ui.next` は 4 スコープ・12 箇所                               |
| 完全一致するスコープ            | `ui.list` = `overlay.list`（13 キー） | 兄弟スコープの丸写し                                              |
| Insert 以外で `uiRole` を書く量 | 115 字符                              | 5 役割の否定列挙が 11 回                                          |

複雑さの原因は「グループ化の不足」ではありません。**条件がキーに付いている**ことです。条件は 16 通りしかないのに、キーごとに書き直しているため、次の 4 つの問題が生じています。

1. **重複**: 同じ条件文字列を何度も書く。修正時に書き漏らすと挙動が分岐する。
2. **暗黙の順序依存**: 同じキーが複数スコープに出るため「後に書いたものが勝つ」が仕様になる。並べ替えが挙動変更になる。
3. **否定条件の再列挙**: `uiRole` が未設定の状態を表現する手段が無いため、5 役割すべての否定を書く。役割を足すと 3 か所を直す必要がある。
4. **写し間違い**: `ui.list` と `overlay.list` のように、同じキー表を 2 か所に複製している。

ADR 0024 は「既定キーは 1 か所（`builtin/keymaps/default.json`）に置き、ヒント文字列もそこから生成する」と決めました。この決定は維持します。変えるのは **1 か所の中の構造**です。

## 決定ドライバ

1. **挙動不変**: 既存のキー解決結果を 1 件も変えない。リファクタと機能変更を混ぜない。
2. **明示性の維持**: どのキーがどの条件で効くかを、ファイルを読めば分かること。暗黙の継承で追跡不能にしない。
3. **単一の情報源**: 同じキー表・同じ条件を 2 か所に書かないこと。
4. **順序非依存**: ファイルの行を並べ替えても挙動が変わらないこと。
5. **拡張性**: 役割やサーフェスを足すとき、1 か所の変更で済むこと。
6. **互換性**: `init.ts` の `keymap.bind({ keys, command, when })` と、`unbind` の件数・ヒント生成の意味を変えないこと。
7. **小さな実装**: `crates/vy-app/src/keymap.rs` のローダーだけを差し替え、実行時の照合ロジックには触れないこと。

## 検討した選択肢

| 選択肢                                   | 内容                                                                             | 評価                                                                                |
| :--------------------------------------- | :------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------- |
| A. プリセット定数 + グループ             | `when` 文字列を定数化し、同じ条件のキーをまとめる                                | 行数は減るが条件の所在は変わらない。`uiRole` の否定列挙も残る。暗黙の順序依存も残る |
| B. スコープ宣言 + キーテーブル（採用）   | 条件をスコープに 1 回書き、キーはプロファイルで共有する                          | 重複・順序依存・否定列挙をすべて消せる。ローダーのみの変更で済む                    |
| C. 式言語を廃止し Rust で定義            | `when` を型付きの述語にする                                                      | 最も安全だが、`keymap.setContext` による拡張と `init.ts` の互換を失う。ビルドが要る |
| D. 条件のデータ化（TOML / typed schema） | `when` を構造化データ（`{ paneKind: "editor", mode: { not: "insert" } }`）にする | 表現力は上がるが、否定と集合の表現が冗長になり、読みにくくなる                      |

C を採らない理由は、`Keymap::matches` が `when::Expr` を評価する現在の仕組みを壊すためです。`keymap.setContext` でプラグインが独自の名前を足す経路（`docs/specs/keymap.md` §8）が失われます。

D を採らない理由は、`uiRole == 'list' || uiRole == 'tree' || uiRole == 'table'` のような集合条件を構造化すると、かえって入れ子が深くなるためです。文字列の式は 1 行で読めますが、構造化データでは 5 行になります。

A を採らない理由は、複雑さの原因に届かないためです。条件の文字列を定数に置き換えても、「条件はどのキーに効くか」という関係はキーごとに繰り返されます。順序依存も残ります。

## 決定

既定キーマップを **プロファイル**（キー → コマンドの表）と **スコープ**（条件 + 使うプロファイル）の 2 層に分けます。ファイル名と配置は変えません。

### 構造

```jsonc
{
  "profiles": {
    "nav": {
      "j": "vy.ui.next",
      "down": "vy.ui.next",
      "ctrl-n": "vy.ui.next",
      "k": "vy.ui.prev",
      "up": "vy.ui.prev",
      "ctrl-p": "vy.ui.prev",
      "g g": "vy.ui.first",
      "G": "vy.ui.last",
      "enter": "vy.ui.activate",
    },
    "page": {
      "ctrl-d": "vy.ui.page_down",
      "ctrl-u": "vy.ui.page_up",
      "x": "vy.ui.toggle",
      "y": "vy.ui.yank",
    },
    "focus": { "tab": "vy.ui.focus_next", "backtab": "vy.ui.focus_prev" },
    "tree": { "l": "vy.ui.expand", "h": "vy.ui.collapse" },
    "exline": {
      "up": "vy.ui.history_prev",
      "ctrl-p": "vy.ui.history_prev",
      "down": "vy.ui.history_next",
      "ctrl-n": "vy.ui.history_next",
      "enter": "vy.ui.activate",
      "tab": "vy.ui.complete_next",
      "backtab": "vy.ui.complete_prev",
    },
    "cancel": { "esc": "vy.ui.cancel" },
  },
  "scopes": [
    { "name": "global", "keys": { "esc": "vy.mode.normal" } },
    {
      "name": "notInsert",
      "when": "mode != 'insert' && overlay == 'none'",
      "keys": { ":": "vy.ui.ex_command_line" },
    },
    { "name": "normal", "when": "normalMode", "keys": {/* … */} },
    {
      "name": "editor",
      "when": "paneKind == 'editor' && overlay == 'none' && mode != 'insert'",
      "keys": {/* … */},
    },
    {
      "name": "editor.normal",
      "extends": "editor",
      "when": "normalMode",
      "keys": {
        "o": "vy.mode.open_below",
        "O": "vy.mode.open_above",
        "g v": "vy.edit.last_visual",
      },
    },
    {
      "name": "ui.nav",
      "when": "overlay == 'none' && paneKind == 'ui' && uiRole != 'textInput'",
      "profiles": ["nav"],
    },
    {
      "name": "surface",
      "when": "overlay != 'none' && overlay != 'ex'",
      "profiles": ["nav", "page"],
    },
  ],
}
```

### 規則

1. **`when` はスコープに 1 回だけ書く**。キーは `command` だけを持つ。
2. **`profiles` で同じキー表を共有する**。`ui.nav`・`surface`・`ui.page` は `nav` を参照し、表を複製しない。
3. **`extends` は「同じ条件を引き継ぐ」と読む**。子スコープは親のキーを継承し、同名キーだけを上書きする。継承は明示された 1 本の親だけをたどるので、追跡は 1 ホップで済む。
4. **適用順序は配列の順序で固定する**。同名キーが複数スコープに一致した場合は、**配列で後ろのスコープが勝つ**。現行と同じ規則だが、スコープ単位になるため衝突の見通しがよくなる。同値の重複はローダーがエラーにする。
5. **`keys` の値は文字列 1 本、または配列**。配列は展開時に個別バインディングになる。`unbind("h")` の件数は現行と同じ 3 件のまま。
6. **スコープ名は `when` から参照できる述語になる**。`"when": "ui.nav"` は `ui.nav` の条件を指す。これにより `uiRole` 未設定の否定列挙が 1 か所に収まる。
7. **`uiRole` の未設定を表す述語をローダーが提供する**。`noRole` は「`overlay == 'none'` かつ `paneKind == 'ui'` かつ `uiRole` が未設定」を意味する。役割を足しても否定列挙を直さなくてよい。
8. **`init.ts` の API は変更しない**。`keymap.bind({ keys, command, when })` は従来どおり受け付け、内部的にプロファイル展開後の `Binding` を積む。既定ファイル専用の形式は `load_default` だけが読む。

### 計測結果

上記の構造へ移すと、次のようになります。

| 指標                                    | 現行        | 新形式        |
| :-------------------------------------- | :---------- | :------------ |
| ファイル行数                            | 736         | 約 190        |
| 定義の総数（プロファイル + インライン） | 147         | 89 + 25 = 114 |
| スコープ数                              | （条件 17） | 16            |
| プロファイル数                          | 0           | 6             |
| 展開後のバインディング数                | 147         | 127           |
| 最長の条件文字列の出現回数              | 44          | 1             |
| 同一キー表の複製                        | 1 組        | 0             |

展開後のバインディングが 147 から 127 に減るのは、`ui.list` と `overlay.list` の丸写し（13 キー）と、`ui.nav` 系 4 スコープに散っていた同一コマンド（`vy.ui.next` など）がプロファイルに集約されるためです。解決結果は変わりません。

### 挙動不変の検証

移行前に、現行ファイルを評価する参照実装と、新形式を展開する試作実装を用意し、全コンテキスト（`paneKind` 4 種 × `overlay` 8 種 × `mode` 2 種 × `uiRole` 6 種 × operator/textObject の有無）についてキー解決結果を比較しました。実際に到達しうる 160 コンテキストで **差分 0 件** を確認しています。

この比較はテストとして残します。`crates/vy-app/src/keymap.rs` に、`(context, key) → command` の表を固定したネットワークテストを置き、リファクタ後も同じ表になることを検証します。テーブルは現行ファイルから生成し、テストデータとして埋め込みます。

### 重複の解消

プロファイル化に伴い、次の重複を解消します。

- `uiRole` の 5 役割の否定列挙（11 回）→ `uiRole != 'textInput'` と `noRole` の 2 種類に集約。
- `overlay == 'palette' || … || overlay == 'settings'`（1 回）→ `surface.modal` スコープへ。`overlay != 'none'` との差分だけを書く。
- `vy.ui.next` / `vy.ui.prev` / `vy.ui.first` / `vy.ui.last` / `vy.ui.activate` の 4 重複 → `nav` プロファイル 1 か所。
- `vy.ui.activate` の 5 重複 → `nav` と `exline` の 2 か所（Ex は履歴キーを持つため別プロファイル）。
- `ui.list` と `overlay.list` の丸写し → 両方が `nav` + `page` を参照。

## 帰結

### 良い面

- 条件が 1 か所に集まり、キーの追加は 1 行、条件の変更は 1 行で済む。
- 同じキー表の複製が無くなり、片方だけ直す事故が起きない。
- 並べ替えで挙動が変わらない。差分レビューで「順序の入れ替え」を無視できる。
- `uiRole` を足すときに直す場所が 1 か所になる。
- スコープ名が述語になるため、`noRole` のような否定条件をファイル側で再利用できる。

### 悪い面

- 間接参照が 2 段（スコープ → プロファイル）になる。プロファイル名からキーを探す手間が増える。
- 展開後のバインディング数が 127 に減るため、`unbind` の件数を数えているテストは更新が必要。解決結果は変わらないが、件数の期待値は変わる。
- `extends` の継承は「親のキーを子が持つ」と読む必要がある。ファイルを部分だけ読むと、キーがどこから来たか分からない。
- スキーマが 2 層になるため、ローダーの検証コードが増える（未定義プロファイル・循環 `extends`・未使用スコープの検出）。

### 見直す条件

- ユーザーが `~/.config/vy` に独自のキーマップ JSON を置けるようにするとき。そのときは既定ファイルの形式をそのまま公開形式にするか、専用の簡単な形式を用意するかを決め直す。
- プロファイルが 10 個を超え、名前の解決が負担になったとき。そのときはプロファイルを廃止し、スコープ間の継承だけで表現する。

## 実装計画

1. **ADR の登録**: 本 ADR を追加し、`docs/adr/README.md` の「改善・保守」に載せる。
2. **ローダーの差し替え**: `crates/vy-app/src/keymap.rs` の `BindingSpec` を `KeymapSpec { profiles, scopes }` に置き換え、`load_default` で展開する。`Binding`・`feed`・`matches` は変更しない。
3. **検証の追加**: 未定義プロファイル、循環 `extends`、同スコープ内のキー重複、未使用プロファイル、展開後のバインディング重複をエラーにする。
4. **ネットワークテスト**: 現行ファイルから生成した `(context, key) → command` の表を fixture として埋め込み、展開結果が一致することを検証する。
5. **既定ファイルの移行**: `builtin/keymaps/default.json` を新形式へ書き換える。
6. **仕様の更新**: `docs/specs/keymap.md` §8 に、プロファイルとスコープの規則、適用順序、`noRole` の意味を追記する。
7. **検証コマンド**: `cargo test --workspace`、`cargo clippy --workspace --all-targets`、`cargo fmt --all --check`、`pnpm format:check` を通す。

段階を分ける場合は、2〜4 を先にマージし、5〜6 を次のコミットにします。1 コミットでも成立しますが、差分が大きくなるため、レビューは 2 段に分けるほうが安全です。
