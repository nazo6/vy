# ADR 0005: プラグイン UI はネイティブのウィジェット木で作る

- 状態: 採用
- 日付: 2026-10-22

## 文脈

Vy はモーダル編集を中心に据えています。プラグインが提供する UI
でも、同じキーマップ、モード、カウント、`when`、IME
の前編集が効く必要があります。

当初は、自由な見た目を優先して Webview を UI の主な手段にする想定でした。しかし
Webview は OS
のネイティブビューで、キー入力とフォーカスを自分で持ちます。ホストのキーマップは
Webview の中のキーを見られず、Webview の中では vim
の操作を再現できません。プラグインごとにキーバインドがばらつき、利用者が変更できない領域ができます。

[ADR 0001](./0001-ui-framework.md) は Webview
を埋め込めることを求めています。この決定は 0001 を置き換えず、Webview の用途を
Web の文書に限定します。

## 決定ドライバ

1. フォーカス中の UI でも、キーマップ、モード、カウント、`when`
   が同じように効くこと。
2. 利用者がキーバインドを一貫して変更できること。プラグインが生のキーを握らないこと。
3. IME の前編集と、モードの切り替えが正しく動くこと。
4. テーマに追従し、ライトとダークを切り替えても崩れないこと。
5. リモート接続でも同じ形で動くこと。木はクライアント、データはコアに置く。
6. 入力の遅延を増やさないこと。
7. 1人から2人で維持できる実装量に収まること。

## 検討した選択肢

| 選択肢                     | 内容                                     | 問題                                                                          |
| :------------------------- | :--------------------------------------- | :---------------------------------------------------------------------------- |
| Webview を既定にする       | HTML と JS で自由に描く                  | キーマップ、モード、IME、テーマを共有できない。プラグインごとに操作がばらつく |
| ネイティブのウィジェット木 | プラグインが木を渡し、クライアントが描く | 部品の表現力が上限になる。部品を増やす必要がある                              |
| 即時モードの UI            | 毎フレーム JS の関数を呼ぶ               | QuickJS をフレームごとに回すコストが読めない。木の差分より重い                |
| 独自の HTML 風 DSL         | マークアップを解釈する                   | 実装と学習のコストが増える。結局は同じ木に落ちる                              |
| テキストグリッドだけ       | telescope 風の一覧とプロンプト           | 画像、グラフ、リッチテキストが作れない                                        |

## 決定

プラグインの UI
は、クライアントが描くネイティブのウィジェット木で作ります。Webview
は最終手段です。

- ビューの種類に `ui` を加えます。プラグインは `views.register` で `kind: "ui"`
  のビューを登録し、`render` からウィジェット木を返します。
- 木はクライアントが保持し、`id`
  をキーに差分を適用します。レイアウト木と違い、コアには置きません。入力のたびに往復させないためです。
- プラグインは生のキー入力を受け取りません。キーマップがコマンドに解決し、フォーカス中のウィジェットが対応するアクションとして受け取ります。文字入力だけは、insert
  モードの間、フォーカス中のテキスト入力へ直接渡します。
- ウィジェットの操作対象はコマンド ID
  で指定します。クリックとキー入力を同じ経路に通すためです。
- 色、余白、文字の大きさはテーマのトークンで指定します。生の値は書けません。
- Webview は、Notebook の出力、HTML、外部の埋め込みなど、Web
  の文書そのものを表示するときに限ります。操作を伴う UI には使いません。
- Webview を使う場合も、外側のフォーカス、`Esc`
  での離脱、テーマの配信はホストが持ちます。Webview
  の中のキーバインドは保証しません。

## 帰結

### 良い面

- プラグイン UI でも vim の操作が一貫して効きます。
- 利用者がキーバインドを1か所で変更できます。
- IME とテーマがエディタと揃います。
- 木はクライアントにあるため、操作から描画までがローカルで完結します。
- リモート接続では、データだけをコアから取ります。

### 悪い面

- 部品の表現力が上限になります。グラフや複雑な可視化は作れません。
- 部品とホストの実装量が増えます。マークダウン、コードハイライト、テキスト入力、フォーカス管理は自前で持ちます。
- 汎用の UI フレームワーク（React など）は使えません。

### 緩和策

- 部品を合成可能にし、一覧、ツリー、表、フォームを少ない組み合わせで作れるようにします。
- マークダウンは既存の Rust
  のパーサを使い、エディタと同じハイライトを共有します。
- 表現できないものだけ Webview
  に逃がします。逃がしたものは、キー操作をホスト側のコマンドとボタンに出す。

## 見直しの条件

1. 部品の不足で Webview を使う UI が、プラグイン UI の3割を超えたとき。
2. ウィジェット木の差分適用が、入力の遅延として感じられたとき。
3. 部品の数が増え、保守が週の作業時間を圧迫したとき。
