# ADR 0008: プラグイン API を宣言マクロで一本化する

- 状態: 置き換え済み（名前空間の宣言方法は [0013](./0013-host-api-traits.md) で
  trait に置き換え。0007 のメソッド表・dispatch・codegen の一部を置き換え、型の
  置き場所と生成の入り口は [0009](./0009-api-types-live-with-handlers.md) で置き換え）
- 日付: 2026-10-24

## 文脈

ADR 0007 は、境界の型とメソッド表を `vy-api-schema` に置き、shim と d.ts
をそこから生成する方針を決めました。この方針で型のドリフトは減りましたが、メソッドを
1 つ足すたびに次の場所を同期する必要が残りました。

1. `HostCall` の variant と wire 名
2. `HOST_METHODS` の表
3. `plugin_host.rs` の網羅 match
4. `shim.js` の糖衣
5. `overrides.d.ts` の宣言
6. `codegen.rs` の `TOP_LEVEL`、`SUGAR`、`EXTRA_TYPES` などの一覧

特に 3 は型で守られていますが、追加のたびに編集が必要です。表と match
が一致していることをテストで確かめても、同期作業そのものは残ります。

## 決定ドライバ

1. **追加コスト**: メソッドの追加が 1 箇所で完結すること。
2. **単一情報源**: 型・名前・doc・TS 宣言が同じ定義から出ること。
3. **検証容易性**: 生成物が読めて差分をレビューできること。
4. **依存の小ささ**: 実行時の依存を増やさないこと。
5. **段階移行**: 既存のテストを通したまま名前空間ごとに移行できること。

## 検討した選択肢

| 選択肢                                     | 内容                                                                                                                                        | 評価                                                                                    |
| :----------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------ | :-------------------------------------------------------------------------------------- |
| A. `inventory` による自動登録              | 関数属性マクロがリンカセクションに宣言を登録する                                                                                            | 追加が最も楽だが、リンカセクション依存と登録順の非決定性が増える                        |
| B. インライン `mod` への属性マクロ（採用） | `#[vy_api_namespace] mod api { ... }` が内側の関数を列挙し、`METHODS` と `dispatch` を生成する。`#[vy_api_registry]` がモジュールを連結する | 依存がなく、列挙順も決定的。ファイルごとに `mod api { ... }` と `pub use` が 1 行増える |
| C. 中央の一覧マクロ                        | 1 つのマクロ呼び出しに全メソッドを列挙する                                                                                                  | メソッドごとの追記が残り、現状の同期コストが減らない                                    |
| D. `build.rs` でソース走査                 | 属性を探してレジストリを生成する                                                                                                            | cfg とマクロ展開を扱えず、壊れやすい                                                    |

## 決定

### 1. ハンドラ関数が宣言であり、マクロがレジストリを作る

名前空間はインライン `mod` で包み、`#[vy_api_namespace("path")]`
を付けます。マクロは `#[vy_api_method]` の付いた関数を列挙し、次を生成します。

- `MethodDecl`（wire 名、params / result の TS 名、doc、`manual`）
- 引数の復元と `Reply<T>` の直列化を行うアダプタ
- `METHODS`（メソッド名 → ハンドラ）
- `NAMESPACE`（パス、doc、糖衣インターフェース名）
- その名前空間の `dispatch`

`api/mod.rs` の `#[vy_api_registry] mod namespaces { mod ...; }`
が、各モジュールの `METHODS` / `dispatch` / `NAMESPACE`
を連結します。手書きの一覧は `mod` 宣言（名前空間ごとに 1 行）だけになります。

wire 名は既定で「名前空間パス + camelCase(関数名)」です。例外は
`#[vy_api_method("wire.name")]` で上書きします。

### 2. TypeScript の型名は ts-rs から取る

`MethodDecl` の params / result は文字列ではなく `fn() -> String`
として保持し、`TS::name` の結果を格納します。`Option<T>` は `T | null`、`Vec<T>`
は `Array<T>`、`()` は `null` になるため、手書きの TS 型文字列は不要です。

### 3. 糖衣はコールバックとイベント購読だけに減らす

位置引数、ビルダー、ハンドル、`Document` ラッパー、`editor.open` などの command
経由ラッパーは、API を「オブジェクト 1 個 → Promise」に統一して廃止します。 JS
側に残すのは、ホストから JS の関数を呼ぶためのコールバック登録と、イベント購読の
汎用レジストリだけです。メソッドの forwarder は shim の Proxy が名前空間ごとに
生成するため、`__vy_spec` の注入やメソッド表の受け渡しは不要です。ウィジェット
ツリーは `WidgetNode` のリテラルで書き、任意フィールドを `#[ts(optional)]`
にしてビルダーなしでも短く書けるようにします。

### 4. イベントは topic と購読メソッドで宣言する

イベントは `#[vy_api_event("config.onDidChange", payload = ConfigChange)]`
を付けた マーカー const で宣言します。topic の末尾は `on`
で始め、そのまま購読メソッド名に なります。ホストは
`ScriptTask::Emit { topic, payload }` を送り、shim の `__vy_emit`
が購読者へ配ります。shim は Proxy のプロパティ名が `on` で始まるかで
イベントとメソッドを区別するため、イベント一覧の注入も不要です。

### 5. 生成物はコミットし、テストで再生成する

これまでどおり `packages/vy-api-types` と `packages/vy-api`
の生成物はコミットし、CI で `git diff --exit-code` を検査します。生成の入り口は
`cargo test --workspace export_bindings` です。

> 追記: 生成の入口は [0014](./0014-api-codegen-cli.md) で
> `cargo run -p vy-api-codegen -- client` に移しました。

## 帰結

### 良い面

- メソッドの追加が「ハンドラ関数を書く」だけで済み、表・match・shim
  の追記が不要になる。
- doc コメント、型、wire 名、TS
  宣言が同じ関数から出るため、同期漏れが起きにくくなる。
- 列挙順が決定的で、リンカセクションに依存しない。

### 悪い面・課題

- 名前空間ファイルごとにインライン `mod` と `pub use` の 1 行が増える。
- 属性マクロの解析対象が増えるため、マクロ自体のテストが必要になる。
- 既存 API の糖衣を廃止するため、`examples/` と docs の移行が必要になる。

### 緩和策

- Phase 1 では PoC（`editor.mode` /
  `editor.setMode`）だけを新しい経路に移し、残りは旧 dispatch
  にフォールバックした。Phase 2 で全メソッドを移行し、旧 dispatch を削除した。
- 生成物の差分は d.ts と `HostMethods.ts` に限定し、レビューはスキーマ側で行う。

## 見直しの条件

- 名前空間モジュールの `pub use` が煩雑になり、ラッパー呼び出し形式
  （`vy_api_namespace! { ... }`）へ変えたくなったとき。
- イベントが増え、購読の生成をマクロの外へ出す必要が出たとき。
- 宣言の数が増えてコンパイル時間が問題になったとき。

## 関連する未決定事項

- `fs.readFile` の戻り値をプロトコル側で `Uint8Array` 相当にするか。
- イベントのフィルタ（`config.onDidChange` のキー指定など）を型で表すか。
- `views.render` の再描画をホスト主導にするか。
