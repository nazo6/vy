# ADR 0020: プラグインはソース形態とバンドル形態の2つを許す

- 状態: 採用（実装済み。検証の詳細は 0021）
- 日付: 2026-10-24

## 文脈

外部プラグインは `dist/frontend.js` などの単一ファイルを読む前提でしたが、その
バンドルを作る手段がありませんでした。TypeScript のプラグインをそのまま書き、
外部ライブラリも使えるようにする必要があります。

QuickJS の loader に Node 相当の解決を実装すると、`exports` マップ、CommonJS
interop、TypeScript の path alias、symlink、dynamic import、アセットを自前で
扱うことになります。しかもリモートの backend は1ファイルのバンドルを送る設計
（[ADR 0011](./0011-backend-plugins-on-core.md)）なので、実行時解決はローカル
専用の近道になります。

一方で、小さなプラグインにまでビルドを必須にすると、`init.ts` と同じ気軽さが
失われます。

## 決定ドライバ

1. 簡単なプラグインはビルドなしで書けること。
2. 外部依存を使うプラグインは確実に配布できること。
3. 実行時に Node の解決を実装しないこと。
4. リモートでも同じ配布物を使えること。
5. プラグインのルート外を読まないこと。
6. Vy がバンドラを保守しないこと。

## 検討した選択肢

| 選択肢 | 内容 | 評価 |
| :--- | :--- | :--- |
| A. 実行時に `node_modules` を解決 | QuickJS の loader に Node 相当の解決を実装する | 実装量が大きく、CJS interop とリモート経路が二重になる |
| B. 常にバンドル | すべてのプラグインにビルドを要求する | 配布は単純だが、小さなプラグインにもツールチェーンが要る |
| C. 2形態（採用） | ソースは相対 import だけ、外部依存はバンドル | 簡単なものはビルドなし、複雑なものは確実に配布できる |

## 決定

### 1. ソース形態

- `plugin.json` の `main` は `.ts` を指せます（例: `frontend.ts`）。
- 相対 import だけを許可します（`./`、`../`）。
- 探索順は、指定パス、`.ts`、`.js`、`.mjs`、ディレクトリなら
  `index.ts` / `index.js` です。
- JSX と `.tsx` は扱いません。QuickJS に JSX のランタイムがなく、UI は
  ウィジェット木で作るためです。
- `vy` はグローバルなので import は不要です。
- 裸の specifier（`vy-api` を含む）、`node:*`、`node_modules`、`.json`、WASM、
  `require` は許可しません。裸の specifier には「バンドルしてください」と返します。
- ルートはプラグインのディレクトリです。`canonicalize` してルート外に出ない
  ことを確認します。`init.ts` のルートは `~/.config/vy` です。
- 読み込んだファイルを記録し、どれかが変わったらランタイムを作り直します。

### 2. バンドル形態

- `dist/frontend.js` などの単一 ESM ファイルです。依存をすべて含みます。
- `vy` はグローバルなので external 指定は不要です。
- ビルドは esbuild、tsup、rolldown-vite などに任せます。Vy はバンドラも
  `vy plugin build` も持ちません。
- 参考コマンドをテンプレートに置きます。

```sh
esbuild frontend.ts --bundle --format=esm --platform=browser --target=es2022 \
  --outfile=dist/frontend.js
```

- `package.json` とロックファイルは作者が管理します。Vy は当面検証しません。

### 3. backend とリモート

- `backend.ts` は常にバンドルします。`plugin/load` で1ファイルを送る ADR 0011 の
  前提を保つためです。
- フロントのソース形態はクライアント上で動くので、リモート接続でもそのまま
  使えます。

### 4. ロード時の検証

- バンドル形態は module specifier を持たないことを確認します。`vy` はグローバル
  なので import 自体が不要です。持つ場合はエラーにします。
- サイズ上限と SHA-256 を計算し、`plugin/load` と承認の記録に使います。
- `engines.vy` を確認します。
- ソース形態は resolver で、ルート制限、拡張子、裸 specifier の拒否を行います。

### 5. 型検査

- Oxc は型を除去するだけで検査しません。作者は `tsc --noEmit` を使います。
- テンプレートに `tsconfig.json` と `env.d.ts` を置きます。

### 6. Web API

- `console`、`TextEncoder`、`setTimeout` などのプリミティブは後回しにします。
- ただし `crates/vy-js/src/shim.ts` がイベント listener の catch で
  `console.error` を呼んでいるため、二次例外を避ける最低限の修正を行います
  （no-op かホストの `log` に置き換える）。
- 外部ライブラリがこれらを要求する場合は、対応を足すまで動きません。バンドルは
  解決と CommonJS interop を解決しますが、グローバルの欠落は解決しません。

## 帰結

### 良い面

- 簡単なプラグインはビルドなしで書けます。
- 外部依存を使うプラグインはバンドルで確実に配布できます。
- 実行時に Node の解決を持ち込みません。
- リモートの backend は単一ファイルのままです。
- Vy はバンドラを保守しません。

### 悪い面・課題

- 「ソース形態」と「バンドル形態」の2つを説明する必要があります。
- ソース形態はルート制限とリロードの実装が要ります。
- 外部ライブラリの互換性は Web API の有無に依存します。
- ソース形態とバンドル形態で挙動が変わり得ます（型除去の有無、CommonJS
  interop の有無）。
- 配布物の再現性は作者のツールチェーンに依存します。

### 緩和策

- テンプレートと参考コマンドを用意します。
- 裸の specifier にはバンドルを促すエラーを返します。
- ソース形態のテストに、相対 import、循環 import、型だけの import、ルート脱出、
  裸の specifier を含めます。
- backend は最初からバンドルのみと明記します。

## 見直しの条件

1. Web API のプリミティブを足すとき。
2. ソース形態のプラグインが増え、ビルドなしの需要が確認できたとき。
3. 配布物の再現性やハッシュを Vy が保証する必要が出たとき。
4. バンドルサイズがリモート転送で問題になったとき。

## 関連する未決定事項

- ソース形態の探索順をどこまで Node に寄せるか（`package.json` の `exports` は
  対象外）。
- `init.ts` の複数ファイル化と、依存を使う場合の `init.js` の扱い。
- プラグインの承認に内容ハッシュを含めるか。
- `vy` のプロパティを freeze するか（[0019](./0019-global-vy-api.md) と共通）。
