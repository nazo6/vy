# ADR 0021: バンドル検証とエントリの制限

- 状態: 採用
- 日付: 2026-10-24
- 拡張子の扱い、サイズ上限、ハッシュの計算、`engines.vy` の規範は [`plugin-system.md`](../specs/plugin-system.md) を正とします。

## 文脈

[ADR 0020](./0020-plugin-source-and-bundles.md) で、プラグインをソース形態と
バンドル形態の2つに分け、バンドルは単一の ESM とすることにしました。ただし、
どの拡張子をどちらの形態として扱うか、パスをどこまで制限するか、サイズ上限や
ハッシュをいつ計算するかは決まっていませんでした。

検証をロード時まで遅らせると、壊れたバンドルやプラグインの外を指すパスが
承認 UI や起動処理に入り込みます。また、リモートの `backend.ts` は1ファイルを
送る前提なので、残った import を実行時に解決する経路を作れません。

## 決定ドライバ

1. 実行時に Node の解決を持ち込まないこと。
2. 壊れたプラグインを早い段階で除外できること。
3. プラグインのルート外を読まないこと。
4. 将来の `plugin/load` で使えるハッシュとサイズを持つこと。
5. 作者に不要なマニフェスト項目を増やさないこと。

## 検討した選択肢

| 選択肢                          | 内容                                             | 評価                                         |
| :------------------------------ | :----------------------------------------------- | :------------------------------------------- |
| A. 拡張子で形態を決める（採用） | `.ts` はソース、`.js` / `.mjs` はバンドル        | マニフェストが増えず、配布物とも一致する     |
| B. `format` を明示する          | `plugin.json` に `"format": "source"` などを書く | 明示的だが、作者の記述と不整合を起こせる     |
| C. 全ファイルを検証する         | ソースも discovery 時に import を解析する        | ソースの実行時解決と二重になり、保守が増える |

## 決定

### 1. エントリの形態

| 項目      | 許可する拡張子 | 扱い                 |
| :-------- | :------------- | :------------------- |
| `main`    | `.ts`          | ソース形態           |
| `main`    | `.js` / `.mjs` | バンドル形態         |
| `backend` | `.js` / `.mjs` | バンドル形態（必須） |
| それ以外  | 不可           | `.tsx` と JSX も不可 |

`main` の `.js` はソース形態としては扱いません。ビルドなしで書きたい場合は
`frontend.ts` を使います。`backend` に `.ts` を指定した場合は、バンドルして
`.js` にするようエラーにします。

### 2. パスの制限

- `main` と `backend` はプラグインのディレクトリからの相対パスにします。
- 絶対パス、`.`、`..` を含むパスは拒否します。
- プラグインのディレクトリとエントリを `canonicalize` し、エントリがルートの
  内側にあることを確認します。シンボリックリンクで外に出る場合も拒否します。
- 宣言されたエントリは存在するファイルでなければなりません。見つからない
  プラグインは discovery の警告になり、読み込まれません。
- リロード時にもう一度検証します。起動後にバンドルが書き換わっていても、
  古い検証結果を信用しません。

### 3. バンドルの検証

バンドルは UTF-8 の JavaScript として読み込み、Oxc で ESM として解析します。

- 静的 import、`export ... from`、動的 `import()` を拒否します。
- `require()` を拒否します。CommonJS の相互運用はバンドル側で解決します。
- TypeScript と JSX の構文は拒否します。バンドルはビルド済みの JavaScriptです。
- サイズ上限は 4 MiB とします。
- SHA-256 とサイズを計算し、`PluginEntry` に保存します。フロントではログに
  出し、将来の `plugin/load` と承認の記録に使います。

`vy` はグローバルなので、`vy-api` を含む import はすべて不要です。

### 4. `engines.vy`

- `engines.vy` はマニフェストの検証時に `semver` の範囲として解析します。
- 現在の Vy のバージョンと一致しないプラグインは discovery の警告になり、
  読み込まれません。

### 5. ソース形態

ソース形態のエントリ自体は discovery では解析しません。相対 import、拡張子の
補完、ルート制限、裸の specifier の拒否は既存の loader が実行時に行います。
`.tsx` と JSX はエントリの拡張子と Oxc の解析で拒否されます。

## 帰結

### 良い面

- 壊れたバンドルとルート外のエントリが起動処理に入りません。
- バンドルのサイズとハッシュを、リモート転送の前に利用できます。
- マニフェストに形態の項目を増やさずに済みます。

### 悪い面・課題

- `.js` のソースプラグインは書けません。ソース形態は `.ts` に限定されます。
- 4 MiB は初期値で、外部ライブラリの使い方によっては足りなくなる可能性があります。
- ソース形態の構文エラーは、discovery ではなくランタイムの評価時に分かります。
- ハッシュはまだ承認の記録には含めていません。

### 緩和策

- サイズ超過と import の残りは、プラグイン ID とパスを含む警告にします。
- サイズ上限は定数にし、リモート転送を実装するときに見直します。
- ソース形態の作者には `tsc --noEmit` を案内します。

## 見直しの条件

1. リモートの `plugin/load` を実装し、転送上限が決まったとき。
2. `.js` のソースプラグインの需要が確認できたとき。
3. 承認に内容ハッシュを含める必要が出たとき。
4. discovery 時にソース形態も解析したくなったとき。
