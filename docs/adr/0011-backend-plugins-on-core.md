# ADR 0011: バックエンドプラグインはコアで動かし、バンドルをクライアントから送る

- 状態: 採用（実装は Phase 6。backend の型を分ける時期は
  [0019](./0019-global-vy-api.md) で延期）
- 日付: 2026-10-24
- 実装計画と、プロトコル名・API の一覧・上限値の詳細は [proposals/0001](../proposals/0001-phase-6-remote-plugins.md) と [`protocol.md`](../specs/protocol.md) に置きます。この ADR は決定だけを残します。

## 文脈

Vy のプラグインは、クライアントで動く `frontend.ts` と、接続先で動く
`backend.ts` に分かれます。`backend.ts` は、検索、ファイル監視、外部プロセスとの結合など、
データの近くで重い処理をするためにあります。

決定が必要だったのは次の点です。

1. `backend.ts` をどのプロセスで動かすか。
2. プラグインのコードを接続先へどう配るか。
3. フロントとバックエンドの間の API をどう分けるか。
4. ケイパビリティの承認と検査をどこで行うか。
5. プラグインの実行をどこまで隔離するか。

## 決定ドライバ

1. リモート接続でも、データの近くで処理できること。
2. 接続先にプラグインを別途インストールしなくても動くこと。
3. フロントとバックエンドで API の意味を変えないこと。
4. プラグインがケイパビリティの検査を迂回できないこと。
5. 1つのプラグインの失敗がコア全体を落とさないこと。

## 検討した選択肢

### 実行場所

| 選択肢                      | 内容                                                    | 評価                                              |
| :-------------------------- | :------------------------------------------------------ | :------------------------------------------------ |
| A. コアで動かす（採用）     | `vy-server` に `vy-js` を載せ、接続先で評価する         | データの近くで動き、`fs` / `process` を直接呼べる |
| B. クライアントだけで動かす | `backend.ts` もクライアントで評価し、RPC でデータを取る | 重い結果を毎回転送することになり、帯域を使う      |
| C. 別プロセスで動かす       | プラグインごとに子プロセスを立てる                      | 隔離は強いが、プロセス管理と IPC が増える         |

### コードの配布

| 選択肢                          | 内容                                                         | 評価                                                           |
| :------------------------------ | :----------------------------------------------------------- | :------------------------------------------------------------- |
| A. クライアントから送る（採用） | `plugin/load` でバンドルとハッシュを送り、コアがメモリに持つ | 接続先へのインストールが不要。開発中のプラグインもそのまま動く |
| B. 接続先に置く                 | 接続先の `plugins/` から読む                                 | 版のずれと配布の手間が増える                                   |
| C. 共有ストレージ               | ネットワーク越しの共有ディレクトリから読む                   | 環境依存が強い                                                 |

### API の分け方

| 選択肢                    | 内容                                                            | 評価                               |
| :------------------------ | :-------------------------------------------------------------- | :--------------------------------- |
| A. 共通の名前空間（採用） | `fs`、`process`、`workspace` をフロントとバックエンドで共有する | 覚えることが少なく、型の重複もない |
| B. `backend.*` に複製する | `backend.fs` などを別に用意する                                 | 同じ API が2か所になり、ずれる     |

## 決定

### 1. 実行場所とライフサイクル

- `backend.ts` は `vy-server` のプロセス内で動きます。
- プラグインごとに QuickJS のランタイムを1つ作り、グローバルを共有しません。
- `activate(ctx)` と `deactivate()` を持ちます。フロントの `activate` とは別に呼びます。
- フロントの `backend.connect(channel)` が、必要ならバックエンドの読み込みと
  `activate` を待ちます。バックエンドが無い場合は `NotFound`、起動に失敗した場合は
  `InvalidState` を返します。
- バックエンドがクラッシュしてもコアは落とさず、チャネルを閉じます。フロントは
  `onDidClose` を受け取り、必要なら `connect` をやり直します。

### 2. コードの配布

- クライアントは `plugin/load` に `plugin_id`、`version`、`hash`、`bundle`、
  許可済みのケイパビリティ、ワークスペースのルートを入れます。
- コアはサイズとハッシュを検証し、メモリにキャッシュします。ディスクには置きません。
- バンドルは1ファイルの JavaScript です。相対 import と `node_modules` は解決しません。
- アセットは P1 では扱いません。必要になったら `backend.readAsset(path)` を足します。

### 3. API

- フロントとバックエンドで、コアの名前空間を共有します。
  - `workspace`、`documents`、`fs`、`process`、`config`、`log`、`cancellation`
- `backend` はチャネルとライフサイクルだけを持ちます。
  - フロント: `backend.connect(channel)`
  - バックエンド: `backend.registerHandler(channel, handler)`
  - チャネル: `postMessage`、`onMessage`、`request`、`onDidClose`、`dispose`
- バックエンドには UI とクライアント状態を出しません。
  - `ui`、`views`、`panes`、`windows`、`webview`、`notifications`、`progress`、`keymap`、
    `commands.registerCommand`
  - `editor.activeDocument`、`editor.mode`、`editor.selections`、`editor.setMode`、
    `editor.open`、`editor.reveal`
  - `localFs`、`localProcess`、`clipboard`、`openExternal`、`workspace.state`
- バックエンドの API は、暗黙のアクティブ文書を使いません。URI と範囲を明示的に受け取ります。
- 文書の変更イベントは差分で送ります。初回だけ `openTextDocument(uri)` でスナップショットを取ります。

### 4. ケイパビリティと隔離

- 承認はクライアントの `trusted.json` で行います。
- 検査はコアで行います。`plugin/load` で受け取った許可済みのケイパビリティと、
  JS のコンテキストを対応づけます。トークンは JS の引数に出しません。
- `${workspace}` と `${home}` は、接続先のルートで展開します。
- `process` は宣言されたコマンドだけを起動し、シェルを既定で使いません。
- メモリ上限、`activate` の時間上限、handler の時間上限を設けます。
  長時間の処理はストリームとキャンセルで分割させます。
- ログは接続先の `logs/plugins/<pluginId>.log` に書きます。

### 5. プロトコル

- `plugin/load`、`plugin/unload`、`plugin/message` を追加します。
- `plugin/message` はフロントからバックエンドへの要求と、バックエンドからフロントへの
  一方向のメッセージを持ちます。大きな結果は既存の `Stream` を使います。
- 1つのメッセージの上限を決め、超える場合はストリームに分割します。

## 帰結

### 良い面

- リモートでも、検索やファイル監視をデータの近くで実行できます。
- 接続先にプラグインを配る運用が不要です。
- API がフロントと共通なので、コア側の処理をバックエンドへ移しやすいです。
- ケイパビリティの検査をコアに集約できます。

### 悪い面

- コアがクライアントから送られた JavaScript を実行します。信頼の境界が増えます。
- `vy-server` が `vy-js` に依存し、バイナリが大きくなります。
- バックエンドのコードに実体のパスが無いため、`ctx.extensionUri` を提供できません。

### 緩和策

- ハッシュ、サイズ上限、ケイパビリティ検査、実行時間とメモリの上限を必ず通します。
- バックエンドの型は `vy-api/backend` に分け、UI 系の API を型に出しません。
- アセットが必要になったら、バンドルに含めるか `backend.readAsset` で個別に送ります。

## 見直しの条件

1. バックエンドの実行がコアの応答時間に影響する。
2. プラグインのバンドルが大きくなり、転送が問題になる。
3. プラグインごとのプロセス分離が必要になる。

## 関連する未決定事項
