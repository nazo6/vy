# ADR 0032: 浮遊 UI をサーフェスとフローティングペインの 2 層に分ける

- 状態: 提案
- 日付: 2026-10-27
- カテゴリー: architecture
- 実装: 未着手（実装計画は本ドキュメント末尾に記載）

## 文脈

ADR 0024 は、プラグイン UI のフォーカス、コンテキスト、セマンティックアクション、picker のキー経路を決めました。しかし実装はその手前にあり、浮遊する UI を支える土台がありません。

現状は次のとおりです。

- **オーバーレイは 1 個の固定箱**。`crates/vy-app/src/overlay.rs` の `Overlay` は 7 variant（パレット、Ex、引数プロンプト、承認、設定、設定の選択、設定の入力）を 1 つの `Option<Overlay>` に持ちます。寸法は全 variant 共通で、`crates/vy-app/src/ui/palette.rs` の `render_overlay` が上端中央に `560 x 420` の箱を 1 つ描くだけです。`Overlay` 自身は位置も大きさも持ちません。
- **キーはキーマップを通らない**。`crates/vy-app/src/view/mod.rs` の `on_key_down` はオーバーレイが開いている間 `cx.stop_propagation()` で全キーを消費し、`Keymap::feed` に到達しません。キーは `crates/vy-app/src/view/commands.rs` の `handle_*_key` 7 本の固定 `match` に書かれ、コマンド ID を経由しません。そのためパレットや Ex の `Esc`、`Enter`、`j`、`k` を利用者が変えることはできません。
- **コンテキストが無い**。`when` の `KeyContext` が実際に値を持つのは `mode` だけで、`overlay`、`paneKind`、`uiRole`、`uiFocus` は存在しません（ADR 0024 §2 の未実装部分）。
- **プレビューが無い**。`preview` はコード上に一切存在しません。一覧の横に内容を出す経路も、行の高さ以外のレイアウトもありません。
- **フローティングの概念が 2 つに割れている**。`docs/specs/panes.md` §2 は `FloatingPane`（コアが持つペイン、矩形と重なり順、保存対象）と `Overlay`（ペインではない、保存しない）を分けています。一方 `docs/specs/ui.md` §8 は「ペインの外にはみ出すオーバーレイは、ホストが描くものに限る」と、プラグインが独自に浮かせることを禁じています。`docs/specs/panes.md` §3 の `FloatingPane` は未実装で、`layout/get` の `floating` は型なしの空配列です。
- **レイアウトは 2 分木だけ**。`crates/vy-core/src/layout.rs` の `LayoutNode` は `Split` と `Leaf` のみで、z 順も矩形も持ちません。クライアント側では `crates/vy-app/src/view/render.rs` の `update_node_viewports` と `render_node` が同じ比率計算を 2 回実装しています。

やりたいことは 3 つです。telescope のように一覧の横へ選択項目のプレビューを出すこと。パレット、Ex、picker のキーを利用者が再割り当てできること。プラグインが任意の矩形で一時的な UI を浮かせられること。

この 3 つは、同じ「入力とフォーカスを持つ面」の上に乗ります。面のモデルを決めずにキー経路だけ書き換えると、パレット、picker、プレビュー、将来のフローティングで同じ配線を 4 回作ることになります。

## 決定ドライバ

1. **入力の一貫性**: 浮いている面でも、エディタと同じキーが同じ意味で動くこと。
2. **状態の所在**: 表示だけの状態はクライアント、セッションをまたぐ状態はコアに置くこと（[ADR 0003](./0003-editor-state.md)）。
3. **リモート互換**: コアが持つ状態は、リモート接続でも同じ形で復元できること。
4. **実装量**: 1 人から 2 人で維持できる範囲に収まること。
5. **後方互換**: ADR 0024 の決定と、既存のキーマップ・文書の語彙を壊さないこと。
6. **自由度**: プラグインが固有の UI を、生キーを渡されずに作れること。

## 検討した選択肢

| 選択肢                                       | 内容                                                                     | 評価                                                                                     |
| :------------------------------------------- | :----------------------------------------------------------------------- | :--------------------------------------------------------------------------------------- |
| A. 2 層（サーフェス + フローティングペイン） | 一時的な面はクライアント、文書を載せて残す面はコアのペインにする（採用） | 状態の所在が ADR 0003 と一致する。キー経路を 1 本にできる。実装は 2 段階に分けられる     |
| B. すべてコアのペイン                        | 浮いているものもすべて `FloatingPane` にする                             | フォーカスとジオメトリが 1 か所に集まるが、パレットを開くたびに RPC が要り、入力が遅れる |
| C. すべてクライアントのオーバーレイ          | 文書を載せる浮遊ペインもクライアントで持つ                               | 実装は最小だが、`active_pane` と `Ctrl-w` の隣接判定がコアとクライアントに分裂する       |
| D. 現状の `Overlay` を拡張                   | variant ごとに矩形とプレビュー欄を足す                                   | 変更は小さいが、面が増えるたびに `handle_*_key` と描画の分岐が増え、一般化にならない     |

C を単独で採らない理由は、コアが `active_pane` を前提にしているためです。`active_pane` は `editor.open` の既定の開き先、`pane/open` の既定の対象、`CoreHost::document()` の既定文書に使われます（`crates/vy-server/src/session/host.rs`、`pane.rs`）。浮いているペインで文書を開くと、コアは背後のペインをアクティブと見なし、`:e` や既定文書の対象がずれます。

D を採らない理由は、パレットのキーをキーマップへ移す作業が variant ごとに散らばるためです。ADR 0024 §8 が求める「`overlay` 条件で既定キーを引く」形にするには、面の種類を 1 つの状態として扱う必要があります。

## 決定

### 1. 2 層モデルと境界規則

浮遊する UI を、所有者の異なる 2 つの層に分けます。

| 項目           | Surface（サーフェス）                                          | FloatingPane（フローティングペイン）                  |
| :------------- | :------------------------------------------------------------- | :---------------------------------------------------- |
| 所有者         | クライアント                                                   | コア                                                  |
| 実体           | 一時的な面。ペインではない                                     | ペイン。レイアウト木の外に矩形と z を持つ             |
| 保存           | しない                                                         | `workspace-state` に保存する                          |
| 載せられる内容 | ホストが描く UI（一覧、入力、プレビュー、ウィジェット木）      | ビュー（editor、ui、list、text、image、webview など） |
| フォーカス     | クライアントの `FocusPath`                                     | コアの `active_pane`（ペイン間フォーカスの一部）      |
| `Ctrl-w` 移動  | 対象外。開いている間はキーを奪う                               | 対象                                                  |
| 復元           | 復元しない                                                     | 接続時に `layout/get` で復元する                      |
| 用途           | パレット、Ex、picker、プロンプト、承認、設定、ホバー、メニュー | ユーザーが開いて残すフローティングのエディタや端末    |

境界は次の規則で決めます。次のいずれかに当てはまるならフローティングペイン、それ以外はサーフェスです。

1. エディタの文書を表示する。
2. セッションをまたいで残す。
3. `Ctrl-w` の移動対象にする。

この規則により、**文書はサーフェスに載せません**。telescope のプレビューは文書ではなく、ホストが描く読み取り専用の内容として扱います（§8）。

### 2. サーフェスのデータモデル

```text
Surface
  id: SurfaceId
  kind: SurfaceKind        // palette | picker | ex | prompt | approval | settings | hover | menu | custom
  owner: SurfaceOwner      // host | plugin(id)
  placement: Placement     // floating { rect } | bottomBar { height }
  z: u32
  modal: bool
  focus: FocusPath         // ルートからフォーカス中のノードまでの id の列
  restore: RestoreTarget   // 閉じたときに戻すサーフェスかペイン
  content: SurfaceContent  // ホストが描く一覧・入力・プレビュー・ウィジェット木
```

- `SurfaceKind` は閉じた集合です。増やすときは `when` の値と既定キーの表を同時に更新します。
- `placement` は 2 種類に限ります。`floating` は任意の矩形、`bottomBar` は Ex 用の下端固定です。Ex は現状どおりステータスラインの下にあり、矩形も z も持ちません。入力、フォーカス、Esc の層、キー経路だけを他のサーフェスと共有します。
- `FocusPath` はペイン内フォーカス（ADR 0024 §3）と同じ型を使います。サーフェスと `ui` ペインで別々の仕組みを作りません。

### 3. 矩形の座標系

- 矩形は **コンテンツ領域**（ウィンドウからタイトルバー、ステータスライン、CSD の inset を除いた領域）に対する `0..1` の相対値で持ちます。ピクセルは描画時に計算します。フローティングペインも同じ座標系を使います。
- 相対値だけでは文字が読めない大きさになり得るため、`minWidth`、`minHeight`、`maxWidth`、`maxHeight` をピクセルで併用し、コンテンツ領域に clamp します。
- 既定の配置は、パレットと picker が上端中央、プロンプトと承認が中央、ホバーとメニューがアンカー位置です。すべて `placement.rect` の初期値として表し、特別扱いの分岐を作りません。
- ウィンドウの大きさが変わったときは、相対値を保ったまま再計算します。最小値を下回るときは、コンテンツ領域に収まるよう比率を調整します。

### 4. 重なり順（z）

- 並びは `z` で決めます。同じ `z` のときは、後から開いたものが上です。
- モーダルなサーフェスは、非モーダルなサーフェスより必ず上に描きます。モーダル同士は `z` で決めます。モーダルは同時に 1 つだけ開けます。
- 既定の `z` は、ホバー `100`、メニュー `200`、custom `250`、パレットと picker と設定 `300`、プロンプト `400`、承認 `500` です。利用者とプラグインはこの値を変更できません。

### 5. フォーカスと復元

- キーボードのフォーカスは常に 1 つです。モーダルなサーフェスが開いていればそのサーフェス、無ければ最前面のフォーカス可能なサーフェス、どちらも無ければ `active_pane` です。
- サーフェスは開いた時点のフォーカス元を `restore` に記録し、閉じたときに戻します。復元先が消えていれば `active_pane` へ戻ります。
- `Tab` と `Shift-Tab` は、フォーカス中のサーフェスの `FocusPath` を深さ優先で移動します。ペイン内のウィジェット木と同じ規則です。
- サーフェスは `Ctrl-w` の移動対象にしません。開いている間は、§6 のキー経路が先にキーを受け取ります。
- 再描画でフォーカス中のノードが消えたときは、最も近い生存する祖先へ移り、それも無ければ最初のフォーカス可能なノードへ移ります（ADR 0024 §3 と同じ）。
- フォーカスの履歴はクライアントが `session.json` に保存します。サーフェスそのものは保存しません。

### 6. キー入力の経路

キーの解決順を 1 本にします。

1. フォーカス中のテキスト入力があれば、文字入力と IME の前編集をそこへ渡します。
2. それ以外のキーはキーマップがモードとコンテキストで解決します。
3. `vy.ui.*` なら、フォーカス中のサーフェスかウィジェットのアクションを探します。
4. アクションが無ければホストの既定動作、それも無ければ通常のコマンドとして実行します。

`when` から参照できる値を、ADR 0024 §2 に次の 2 つを加えて確定します。

| コンテキスト | 値                                                                                             | 設定する層   |
| :----------- | :--------------------------------------------------------------------------------------------- | :----------- |
| `overlay`    | `none`、`palette`、`picker`、`ex`、`prompt`、`approval`、`settings`、`hover`、`menu`、`custom` | クライアント |
| `surfaceId`  | 最前面のサーフェスの `id`                                                                      | クライアント |

- `overlay` の値は `SurfaceKind` と同じ名前にします。ADR 0024 §2 の値集合に `hover`、`menu`、`custom` を足しただけで、`palette` と `picker` の意味も ADR 0024 のままです。`palette` はコマンドと文書の一覧、`picker` はプラグインが渡した項目の一覧、`custom` はプラグインが開いたサーフェスです。別名（`surfaceKind` など）は作りません。
- モーダルなサーフェスが開いている間、どのコマンドにも一致しなかったキーは消費します。背後のエディタを動かさないためです。
- 非モーダルなサーフェス（ホバー、メニュー、custom）が開いている間、一致しなかったキーはエディタへ流します。読むための面が入力を奪わないようにするためです。
- 既定キーはすべて `builtin/keymaps/default.json` に置き、`overlay == '...'` と `uiRole == '...'` を条件にします。`handle_*_key` の固定 `match` は、キーからコマンド ID を引く処理に置き換えます。
- テキスト入力中の `Esc`、`Tab`、`Shift-Tab`、`Enter` もキーマップに載せます。例外は `Esc` の層の判定（§7）だけで、これはサーフェスのスタックが行います。

### 7. Esc の層

ADR 0024 §9 の 5 層を置き換えず、非モーダルなサーフェスの層を挟んで 6 層にします。上から順に評価し、最初に該当した層だけを処理します。

1. モーダルなサーフェスが開いている: `cancel` で一時状態を戻す。戻すものが無ければ閉じて `restore` へ戻す。
2. 非モーダルなサーフェス（ホバー、メニュー、custom）が開いている: 閉じる。
3. エディタペインが insert または select 系: normal へ戻し、選択を縮小する。
4. プラグイン UI に一時状態がある、またはビューが `cancel` を上書きしている: `vy.ui.cancel` を実行して止める。
5. プラグイン UI にフォーカスがある: 最後にフォーカスしたエディタペインへ戻す。
6. エディタの normal: ホバーなどの一時表示を閉じる。無ければ何もしない。

`docs/specs/ui.md` §9.2 の 4 層は、この 6 層に合わせて実装時に更新します。

### 8. picker のプレビュー

プレビューは picker のサーフェスの中に置きます。別のサーフェスにしません。選択とフォーカスが picker に属するためです。

- レイアウトは「一覧 | プレビュー」の 2 列です。幅の比率は一覧 `0.55`、プレビュー `0.45` を既定にします。コンテンツ領域の幅が `720px` 未満のときは 1 列に戻し、プレビューを出しません。
- `ui.picker.show({ ..., preview })` の `preview` はウィジェット木です。ADR 0024 §8 の決定（Webview を使わない）を維持します。
- `ui.picker.update({ items?, preview? })` で、選択の変化に合わせて内容を差し替えます。`items` を渡した場合はクライアント側で絞り込み、コマンドの往復をしません。
- 選択が変わるたびにプレビューを更新しますが、`fetch` を使う場合だけデバウンスし、`requestId` が古い応答を捨てます（ADR 0024 §8 の未決定事項をこの形で確定します）。
- 大量の行を出すプレビュー（ファイル全体など）は、ウィジェット木の `Text` を積むのではなく、ホストが描く読み取り専用のテキスト面として扱います。この語彙の追加は未決定事項に残します。

### 9. プラグインが開くサーフェス

`docs/specs/ui.md` §8 の「ペインの外にはみ出すオーバーレイはホストが描くものに限る」を、次の範囲で緩めます。

- `ui.surface.open({ id, rect, tree })`、`ui.surface.update({ id, tree })`、`ui.surface.close({ id })` を追加します。
- 開けるのは **非モーダルなサーフェスだけ**です。モーダルな UI はホストが提供します（picker、プロンプト、承認）。プラグインが入力を奪い続ける状態を作らせないためです。
- 内容はウィジェット木に限ります。生のキー入力は渡しません（[ADR 0005](./0005-native-plugin-ui.md)）。
- `rect` はコンテンツ領域に clamp します。画面外や、タイトルバー・ステータスラインの上には置けません。
- 同じ `id` を開き直したときは、内容を差し替えて `z` を変えません。
- `z` はホストが決めます（プラグインのサーフェスは `250`）。利用者の面より前に出ません。
- ケイパビリティ `ui.surface` を必要とします。この API は Phase 6 で追加し、それまではホスト内部だけでサーフェスを使います。

ADR 0024 の未決定事項「プラグインが独自に開くオーバーレイ」は、この決定で閉じます。フローティングペイン（文書を載せる方）は §10 のとおり別扱いです。

### 10. フローティングペインは今回実装しない

コアが持つ `FloatingPane` は、モデルとプロトコルの余地だけを残し、実装は別のフェーズにします。

- `docs/specs/panes.md` §3 の `FloatingPane`（`rect` と `z`）を正とし、保存先は `workspace-state` にします。サーフェスを `session.json` に保存しないのと対になります。
- `layout/get` と `layout/did_change` の `floating` は、実装時に `{ pane_id, rect, z }` の型付き配列にします。今は空配列のままです。
- `panes.openFloating` と `panes.closeFloating` は P2 のままです。実装条件は、文書を載せたまま残したい浮遊ペインか、`Ctrl-w` で移動したい浮遊ペインが実際に必要になったときです。

**それまでは、文書をサーフェスに載せません。** サーフェスに editor ビューを入れると、コアの `active_pane` と食い違うためです。

### 11. クライアントのジオメトリを 1 か所にする

サーフェスの矩形が増えると、比率計算の実装がさらに増えます。`crates/vy-app/src/view/render.rs` の `update_node_viewports` と `render_node` が同じ計算を 2 回持っている状態を解消し、クライアントに 1 つのジオメトリ計算を置きます。

- 入力は、コンテンツ領域の大きさ、レイアウト木と比率、各サーフェスの `placement` です。
- 出力は、ペインとサーフェスのピクセル矩形です。
- コアは比率と相対矩形（`0..1`）だけを持ち、ピクセルを知りません。リモートでも同じ形になります。

## 帰結

### 良い面

- パレット、Ex、picker、プレビュー、ホバー、メニューが、同じ入力・フォーカス・Esc の仕組みに乗ります。キー経路は 1 本です。
- 利用者は 1 つのキーマップで、エディタ、ペイン内 UI、浮いている面のすべてを再割り当てできます。`overlay == 'palette'` のような条件が実際に効きます。
- picker のプレビューを、別のウィンドウ機構を作らずに実装できます。
- 状態の所在が ADR 0003 と一致します。表示だけの面はクライアント、セッションをまたぐ面はコアです。
- プラグインは、フォーカスや z を奪わずに一時的な UI を出せます。モーダルはホストが提供するため、操作不能な画面を作りにくくなります。
- フローティングペインを後から足しても、サーフェスの実装を作り直さずに済みます。

### 悪い面・課題

- サーフェスのスタック、矩形計算、フォーカスの復元を新しく実装する必要があります。オーバーレイの描画とキー処理の書き直しを伴います。
- `Overlay` を `Vec<Surface>` に変えるため、`Option<Overlay>` を前提にしたコード（描画、IME、キー、設定、承認、picker）を広く触ります。
- キー経路の変更は、既存のパレットと Ex の操作を壊しやすい箇所です。`Esc`、`Enter`、`Tab`、`Ctrl-u`、`:` の予約を整理する必要があります。
- `when` の `overlay` に `hover`、`menu`、`custom` が増えるため、既定キーマップの条件が増えます。
- プレビューはホストが描くため、プラグインは自由なレイアウトを作れません（ウィジェット木の範囲に限る）。

### 緩和策

- 実装をフェーズに分けます。まず ADR 0024 のコンテキストと `vy.ui.*`（浮遊と独立）、次にオーバーレイのキー移行、そのあとにサーフェスのスタック、最後にプレビューとプラグイン API です。
- サーフェスの導入時に、既存の 7 variant を `SurfaceKind` に対応づけます（設定の選択と入力は `settings` の内部状態にします）。新しい面を同時に増やしません。
- 既定キーは `builtin/keymaps/default.json` の 1 か所に置き、ヒント文字列もそこから生成します。固定文字列を残しません。
- プレビューが無いときは 1 列のままです。既存のパレットの見た目を変えません。

## 見直しの条件

1. プラグインがモーダルなサーフェスを必要としたとき（入力の奪い方と承認の設計を見直す）。
2. サーフェスの同時表示が常時 4 枚を超え、z の既定値とフォーカス順では説明できなくなったとき。
3. 文書を載せたフローティングペインが実際に必要になったとき（§10 の条件）。
4. 利用者がサーフェスの位置や大きさを変えたくなったとき（ドラッグと保存の設計が要る）。
5. プレビューに仮想化された読み取り専用テキストが必要になったとき（ウィジェット語彙の追加）。

## 実装計画

### Phase 0: ドキュメント

- 本 ADR を追加し、ADR 0024 の「関連する未決定事項」から参照する。
- `docs/specs/ui.md` §2.1 の `paneId` の記述（実装済みと書かれているが `KeyContext` に存在しない）を修正する。

### Phase 1: コンテキストとペイン内フォーカス（ADR 0024 Phase 1）

浮遊 UI に依存しないため、Phase 0 と並行できます。

- `KeyContext` に `paneKind`、`viewType`、`overlay`、`surfaceId` を追加する（`crates/vy-app/src/keymap.rs`）。`when.rs` の文法は変更しない。
- ペインごとの `FocusPath` と、再描画時のフォールバックを実装する。
- `Tab` / `Shift-Tab` の DFS 移動を実装する。
- `builtin/keymaps/default.json` のエディタ系バインドに `paneKind == 'editor'` を付ける。

### Phase 2: `vy.ui.*` の語彙と既定動作（ADR 0024 Phase 2）

- `vy.ui.next`、`prev`、`pageDown`、`pageUp`、`first`、`last`、`activate`、`cancel`、`toggle`、`yank`、`focusNext`、`focusPrev` を `crates/vy-client-api/src/command.rs` に追加する（`palette: hidden`、Ex 名なし）。
- 移動と選択の既定動作をクライアントの Rust に実装する。コマンド実行キューを通さない。
- `UiActionArgs` と `ui.focused()` を追加する。

### Phase 3: オーバーレイのキー移行（ADR 0024 Phase 3 を 7 variant に拡張）

- `on_key_down` の早期 return を廃止し、文字入力だけを先に分岐して、残りを `Keymap::feed` へ流す。
- `handle_*_key` を「アクションを適用する関数」に分解し、キーからコマンド ID を引く形にする。
- `builtin/keymaps/default.json` に `overlay` 条件付きの既定キーを追加する。`:` の無条件の横取りと、Ex の `Ctrl-u` の予約を解消する。
- `crates/vy-app/src/ui/palette.rs` の `OverlayLabels` をキーマップから生成する。

### Phase 4: サーフェスのスタックとジオメトリ

- `Option<Overlay>` をサーフェスのスタックに置き換える。`id`、`kind`、`placement`、`z`、`modal`、`focus`、`restore` を持たせる。
- 既存の 7 variant を `SurfaceKind` に移す（設定の選択と入力は `settings` の内部状態にする）。Ex は `bottomBar` のままにする。
- サーフェスごとのスクロール状態と `FocusPath` を持つ。`palette_scroll_handle` を 1 個から可変にする。
- クライアントのジオメトリ計算を 1 か所にまとめる（`update_node_viewports` と `render_node` の重複を解消）。
- ホバーとメニューをサーフェスに寄せる。

### Phase 5: picker のプレビュー

- `render_overlay` を「一覧 | プレビュー」の 2 列にする。`720px` 未満では 1 列に戻す。
- `ui.picker.update` と `ui.picker.close` を追加する。
- `preview` をウィジェット木として描画し、選択の変化に追従させる。`fetch` の結果は `requestId` で古いものを捨てる。

### Phase 6: プラグインが開くサーフェス

- `ui.surface.open`、`ui.surface.update`、`ui.surface.close` を追加する。非モーダルに限る。
- ケイパビリティ `ui.surface` を追加し、`rect` をコンテンツ領域に clamp する。
- `docs/specs/ui.md` §8 の制約を、この範囲で更新する。

### Phase 7（任意）: コアのフローティングペイン

- `crates/vy-core/src/layout.rs` に矩形と z を持つフローティングを追加する。
- `layout/get` と `layout/did_change` の `floating` を型付きにする。
- `panes.openFloating` と `panes.closeFloating` を実装する。
- `workspace-state` に保存し、`layout/get` で復元する。
