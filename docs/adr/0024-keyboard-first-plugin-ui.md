# ADR 0024: キーボードファーストなプラグイン UI

- 状態: 採用（実装は未着手）
- 日付: 2026-10-27
- 実装計画: [proposals/0007](../proposals/0007-keyboard-first-plugin-ui.md)（規範の表、作業順序、対象ファイル）

## 文脈

[ADR 0005](./0005-native-plugin-ui.md) は、プラグイン UI をネイティブのウィジェット木で作り、プラグインには生のキー入力を渡さないと決めました。キーはキーマップがコマンドへ解決し、フォーカス中のウィジェットが対応するアクションとして受け取ります。

しかし、実装されているのはグローバルなキーマップからコマンドを実行するところまでで、この構想を支える前提が欠けています。

- ペイン内のウィジェットにフォーカスの概念がなく、UI ペインにフォーカスしてもキーはアクティブ文書のエディタ状態へ流れます。
- `paneKind`、`viewType`、`uiRole`、`uiFocus` といったコンテキスト変数がなく、UI 用のキーとエディタ用のキーを条件で分けられません。
- アクションの語彙と `vy.ui.*` の既定キーが決まっていません。
- picker のキーがホストの固定処理で、プラグインが独自のキーを割り当てられません。
- `views.register` は関数を受け取る設計ですが、ホストから JS の関数を呼ぶ経路がありません。
- `space` は単独でパレットに割り当てられ、`space f f` が成立しません。

telescope.nvim や nvim-tree のような UI をプラグインが作り、エディタと同じキーで動く環境を保つには、フォーカス、コンテキスト、アクションの語彙、ビューの宣言方法を決定として固定する必要があります。

## 決定ドライバ

1. **一貫性**: フォーカスがエディタでもプラグイン UI でも、同じキーが同じ意味で動くこと。
2. **再割当て可能性**: 利用者がキーバインドを 1 か所で変更でき、プラグインがキーを握らないこと。
3. **即応性**: 移動と選択はキーを押すたびにコマンドの往復をしないこと。
4. **リモート互換**: 木とフォーカスはクライアント、データはコアに置けること。
5. **実装量**: 1 人から 2 人で維持できる範囲に収まること。
6. **自由度**: プラグイン固有の操作を、生キーを渡さずに表現できること。

## 検討した選択肢

| 選択肢                                          | 内容                                                                   | 評価                                                                           |
| :---------------------------------------------- | :--------------------------------------------------------------------- | :----------------------------------------------------------------------------- |
| A. フォーカスとセマンティックアクション（採用） | ホストがペイン内フォーカスを持ち、キーを意味のあるアクションへ解決する | 既定キーをホストが提供でき、プラグインは独自の意味だけを足せる。実装量は増える |
| B. プラグインへ生キーを渡す                     | フォーカス中のビューにキーイベントを送り、プラグインが自分で解釈する   | 自由度は最大だが、プラグインごとに操作がばらつき、利用者がキーを変更できない   |
| C. Webview に逃がす                             | 独自 UI は HTML と JS で作り、キーもそちらで扱う                       | キーマップ、モード、カウント、IME を共有できない（ADR 0005 で却下済み）        |
| D. プラグインがキー表を宣言する                 | プラグインがキー列と意味の表をホストへ渡し、ホストが解釈する           | 一貫した既定を作れず、結局はアクションの語彙が必要になる                       |

## 決定

### 1. プラグインに生キーは渡さない

ADR 0005 の決定を維持します。キーは次の順で解決します。

1. キーマップがモードとコンテキストでキー列をコマンドへ解決する。
2. コマンドが `vy.ui.*` なら、フォーカス中のウィジェットのアクションを探す。
3. アクションがあれば実行し、無ければホストの既定動作、それも無ければ通常のコマンドとして実行する。

文字入力だけは、insert モードの間、フォーカス中のテキスト入力へ直接渡します。IME の前編集も同じ経路です。

### 2. ホストがペイン内フォーカスを持つ

- クライアントはペインごとに `FocusPath`（ルートからフォーカス中のノードまでの `id` の列）を持ちます。ペイン間のフォーカスはコアが持つという [ADR 0003](./0003-editor-state.md) の分担は変えません。
- フォーカス可能なのは `list`、`tree`、`table`、`textInput`、`button` です。`Tab` と `Shift-Tab` はアクティブペイン内を深さ優先で移動し、マウスのクリックも同じフォーカスを設定します。
- 再描画でフォーカス中のノードが消えたときは、最も近い生存する祖先へ移り、それも無ければ最初のフォーカス可能なノードへ移ります。
- フォーカスはペインごとに `session.json` へ保存します。木そのものは保存しません。
- キーマップの `when` から参照するコンテキスト（`paneKind`、`viewType`、`uiRole`、`uiFocus`、`uiSelectionCount`、`overlay`）はホストが設定し、プラグインは同じ名前を上書きできません。プラグイン独自の条件は `keymap.setContext` で足します。

### 3. 操作は閉じた語彙の `vy.ui.*` で表す

- プラグイン UI の移動、選択、決定、キャンセルなどは、閉じた集合のコマンド `vy.ui.*` で表現します。語彙を閉じるのは、既定キーをホストが提供し、利用者が同じコマンドを別のキーへ割り当てられるようにするためです。
- `vy.ui.*` はパレットに表示せず、Ex 名も持ちません。実行キューとケイパビリティ検査は既存の経路を通します。
- 移動と選択の既定動作はクライアントの Rust で完結させます。キーを押すたびにコマンドを実行すると、実行キューとタイムアウトを通るため連続操作が遅れます。
- プラグインのコマンドには、アクション名、フォーカス中の `id`、選択中の `id`、展開中の `id`、カウント、レジスタなどを `UiActionArgs` として渡します。プラグインは状態を問い合わせる往復をせずに操作できます。
- プラグインは `actions` でアクション名を自分のコマンド ID に対応づけて上書きできます。同じ情報をコマンド以外の入口から参照するために `ui.focused()` を用意します。

### 4. ビューの宣言はコマンド ID にする

`views.register` の `render` と `restore` を関数からコマンド ID に改めます。ホストから JS の関数を呼ぶ経路を新しく作らないためです。木はプラグインが `views.render` で push し、ホストが差分を適用します。

アクションと復元がコマンドであることで、ケイパビリティ検査と実行キューを既存の 1 本の経路に保てます（[ADR 0022](./0022-command-surfaces.md)）。

### 5. 既定キーを役割ごとに分け、`space` はリーダー専用にする

- 既定キーは `paneKind` と `uiRole` で排他にします。エディタは `paneKind == 'editor' && overlay == 'none'`、プラグイン UI は `uiRole == 'list'` などの条件を付けます。
- `space` はリーダー専用にし、単独の `space` にパレットを割り当てるのをやめて `space space` をパレットにします。これにより `space f f` のような利用者定義が成立します。既存の利用者にとっては破壊的変更です。
- picker のキーもホストの固定処理ではなくキーマップを通し、`overlay == 'picker'` と `uiRole` で既定キーを引きます。プラグインは `Ctrl-s` などの独自のキーを割り当てられます。

### 6. Esc は 5 層で解決する

`Esc` は、オーバーレイ、エディタのモード、プラグイン UI の一時状態と `cancel`、プラグイン UI のフォーカス、エディタの一時表示の順に評価し、最初に該当した層だけを処理します。

各層の条件と、語彙・既定キー・`UiActionArgs`・picker の規則の詳細は [proposals/0007](../proposals/0007-keyboard-first-plugin-ui.md) にあります。実装が完了した時点で仕様書へ移します。

### 7. oil 型の編集可能な一覧は今回決めない

oil.nvim のようにバッファ自体が UI になる方式は、仮想ドキュメントの生成、編集の横取り、保存と破棄の意味を決める必要があります。仮想ドキュメント方式と一覧のインライン編集方式の 2 案を未決定事項として残し、実装は別のフェーズにします。

## 帰結

### 良い面

- プラグイン UI でも、移動、選択、決定、キャンセルがエディタと同じキーで動きます。プラグインは既定キーを定義する必要がありません。
- 利用者は 1 つのキーマップで、エディタとプラグイン UI の両方を再割当てできます。
- アクションがコマンドであるため、ケイパビリティ検査、実行キュー、スクリプトからの実行をそのまま使えます。
- 木とフォーカスがクライアントにあるため、キーから描画までがローカルで完結します。
- picker とビューで同じ一覧の状態機械を共有できるため、telescope 相当と nvim-tree 相当を別々に作りません。

### 悪い面・課題

- アクションの語彙を増やす必要があります。語彙に無い操作はプラグインがキーを明示してコマンドへ割り当てます。
- 一覧、ツリー、表、スクロール、ウィジェット内フォーカスの実装量が増えます。
- picker のキー経路をホストの固定処理からキーマップへ移すため、既存のキー処理を作り直す必要があります。
- `space` の変更は既存の利用者の操作を変えます。
- プラグインがアクションを上書きすると、キーごとにコマンドの実行キューを通るため、連続操作が遅くなる可能性があります。
- UI ペインのモードとステータスラインの表示は、この決定では扱いません。

### 緩和策

- 語彙は最小限から始め、追加の要求が繰り返されたときだけ増やします。
- 移動と選択の既定動作はホストが持ち、プラグインは上書きしたい操作だけを宣言します。
- `UiActionArgs` と `ui.focused()` で、プラグインが状態を問い合わせる往復を減らします。
- `space` の変更は既定キーマップの 1 か所に閉じ、`space space` を案内します。

## 見直しの条件

1. セマンティックアクションの追加が頻発し、語彙が肥大化したとき。
2. アクションをプラグインのコマンドで上書きする操作が、入力の遅延として感じられたとき。
3. プラグインの 3 割以上が生キーか独自のキー表を必要としたとき（ADR 0005 の見直し条件と連動）。
4. picker のプレビューに Webview が必要になったとき（ADR 0005 の Webview の制限を再検討）。
